# 残星会服装店与角色换装系统

## Goal

在现有“扎希拉商铺”窗口内增加可平移切换的“残星会 cosplay 服装店”，让玩家用金币购买角色服装，并在“部员手册 → 角色详情”中为对应角色选择和保存当前服装；服装只改变角色立绘表现，不改变角色身份与技能。

## What I already know

- 商店左下角增加“← 残星会”入口；进入服装店后提供“扎希拉商店 →”返回入口。
- 商店切换发生在同一个窗口内，并使用水平平移动效。
- 服装店桌面端参考图采用“娜波摩在左、最多五件服装在右”的布局。
- 服装店竖屏移动端参考图采用“商品在上、娜波摩与聊天框在下”的布局。
- 娜波摩是残星会看板娘，聊天框显示随机问候语。
- 每件商品卡只展示角色服装立绘与金币售价；点击商品后打开详情，并在详情内购买。
- 服装商品每批最多显示 5 件；已拥有服装不再进入可展示商品池；支持手动刷新。
- 换装入口位于“部员手册 → 角色详情”立绘区；桌面端在右上角，移动端在左上角以避开关闭按钮。
- 点击换装按钮后打开独立顶层窗口，展示该角色的完整服装目录，布局和操作结构参考部员手册角色卡片。
- 点击服装卡片打开该服装详情；点击卡片内独立的衣服图标按钮才执行装扮并立即持久化，不另设保存按钮。
- 未拥有的服装卡片整体灰化，但仍可点击查看详情；其衣服图标装扮按钮不可用。

## Confirmed Constraints

- 服装是纯外观资产，不改变技能、数值、角色 ID、配音或可出战状态。
- 每件服装只属于一个角色，同一角色同时只能装备一件服装。
- 购买成功后不静默自动换装，而是询问玩家是否立即装备；拒绝时仍可稍后从部员手册装扮。
- 换回默认立绘不需要再次购买。
- 残星会与扎希拉商铺使用同一金币余额，但拥有独立商品池、看板娘文案和窗口布局。
- 娜波摩看板娘使用用户提供的挥手透明立绘，不复用角色目录默认站姿；运行时只加载转换后的 WebP。
- 桌面端无需适配后台管理界面的移动布局；玩家端以竖屏移动适配为主。

## Requirements (evolving)

- 同一商店窗口支持扎希拉商铺与残星会服装店两个店面。
- 玩家每次从首页打开商店时始终先进入扎希拉商铺；不记忆上次店面，也不新增首页残星会入口。
- 店面切换使用水平平移动效，并尊重减少动态效果设置。
- 残星会店内采用稍阴暗的戏剧舞台服装店氛围：深红/酒红主色、暗色幕布、暖色局部灯光和少量旧金色舞台细节，不使用参考图中的高饱和绿色占位背景。
- 暗色背景上的商品价格、锁定态、聊天框、金币余额和交互按钮必须保持清晰高对比，状态不能只依赖颜色。
- 两个店面在同一次窗口会话中分别保留当前批次、预加载批次和独立刷新冷却；关闭整个商店后状态销毁，下次打开重新抽取。
- 残星会每批最多展示五件未拥有服装，支持刷新。
- 每批优先随机选择玩家已拥有对应角色且尚未购买的可购买服装；不足五件时，再用未拥有角色的灰色锁定服装补齐。
- 首批内置五件服装：西格莉卡 1 件、达妮娅 2 件、娜波摩 2 件，初始售价统一为 600 金币。
- 首批初始显示名为“西格莉卡·服装 01”“达妮娅·服装 01”“达妮娅·服装 02”“娜波摩·服装 01”“娜波摩·服装 02”，后台可随时修改。
- 首批服装的名称、简介、插画署名、售价、折扣、显示/购买状态和排序均可由后台修改，不写死在玩家端。
- 后台新增独立“服装管理”页，集中维护服装标识、名称、所属角色、立绘、简介、插画署名、售价/折扣、显示状态、购买状态和排序。
- 后台服装管理预留可选“糖果特效立绘”字段；配置后，角色触发糖果效果时优先使用该服装专属变体。
- 普通服装立绘和糖果特效立绘均通过后台填写项目内 `/assets/...` 路径或受支持 URL；当前任务不建设文件上传、存储和清理系统。
- 未配置服装专属糖果特效立绘时，安全回退到现有角色级糖果立绘；回退同样不改写装备记录。
- 后台停用服装后，所有玩家都不能继续装扮；当前装备该服装的角色自动恢复默认立绘。
- 停用不删除玩家的购买所有权；服装重新启用后，原拥有者可再次装扮且无需重复购买。
- “商店显示”关闭只让服装退出残星会商品池，部员手册目录仍展示，已拥有者仍可装扮。
- “可购买”关闭会阻止新购买，但服装仍可在商店和部员手册展示，已拥有者仍可装扮。
- “停用”才会禁止所有人装扮、让当前装备者恢复默认，并把服装排除出商店；所有权记录继续保留。
- 五张源 PNG 按透明有效内容统一视觉占比并转换为稳定方形画布 WebP，避免 800×800 与 1000×1000 源图在商品卡和全局立绘中比例漂移。
- 未拥有对应角色时，其服装仍可出现在商品批次中；商品立绘显示为灰色锁定态。
- 灰色锁定服装允许打开详情预览，但详情购买操作不可用，并明确提示需要先拥有对应角色。
- 商品卡不提供直接购买按钮；购买只发生在商品详情内。
- 服装详情展示服装大图、服装名、所属角色、简短介绍、插画署名、原价/折扣价、持有或锁定状态及购买按钮。
- 购买成功后保持详情打开并把状态更新为“已拥有”，商品卡保留到下一次手动刷新，娜波摩显示感谢台词。
- 娜波摩进店闲置时使用挥手图与随机问候；购买成功切换“谢谢惠顾”图；刷新或没有可展示商品时切换“空或刷新”图。
- 玩家尝试购买但金币不足时使用“空或刷新”图，聊天框固定显示“你是来找茬的吧？”。
- 购买成功后追加“是否装备该服装？”确认弹窗；确认则立即持久化为该角色当前服装，取消则只加入衣柜。
- 部员手册角色详情提供服装选择弹窗，不另设统一保存按钮。
- 角色详情右上角的衣服按钮始终可点击，不以角色所有权或已拥有服装数量为前提。
- 角色本身未拥有时仍可浏览完整服装目录和详情，但所有装扮按钮（包括默认服装）均禁用；不显示额外提示、tooltip 或购买引导。
- 未拥有角色的默认服装卡保持正常外观，只禁用装扮按钮；其他未拥有服装仍按服装所有权灰化。
- 换装弹窗展示该角色的全部服装，而不只显示已拥有服装；卡片主体负责打开详情，卡片内衣服图标按钮负责装扮。
- 换装弹窗使用不限数量的响应式网格滚动：桌面多列、竖屏手机两列，标题和关闭按钮保持可见，不使用分页。
- 换装窗口标题固定为“{角色名}的衣柜”，不显示副标题，也不显示“这个角色暂时只有默认服装”一类解释性空状态文案。
- 换装卡片的详情按钮保持透明、无独立背景和阴影，让外层卡片直接呈现与部员手册角色卡一致的“卡片承载立绘”结构；当前装扮卡的整个外层卡片使用浅绿色背景。
- 衣柜内的服装详情使用独立的全屏顶层遮罩和窗口，与衣柜窗口同级挂载，不嵌在衣柜内容区内。
- 换装目录排序为：默认服装固定第一；当前装扮（若非默认）紧随其后；剩余已拥有服装在前、未拥有服装在后，各组内部按后台排序。
- 每个角色的默认立绘作为永久拥有的“默认服装”卡片固定排在第一张，可查看详情并通过装扮按钮随时换回默认。
- 未拥有服装以灰色锁定卡片显示，详情仍可查看，但装扮按钮禁用；已拥有服装的装扮按钮可用，当前服装只用浅绿色卡片背景表示，不显示“装扮中”之类的附加文案。
- 部员手册中的服装详情只提供预览、状态和价格信息，不允许直接购买；购买只在残星会当前商品批次的详情中进行。
- 部员手册未拥有服装详情不显示“前往残星会”按钮或引导文案，仅展示服装信息与未拥有状态。
- 已保存的服装在该角色于玩家端出现的所有立绘位置生效，包括部员手册、首页、匹配/对局、观战、结算、玩家资料、回放、剧情与招募。
- 多人界面按各玩家各自装备的服装展示；没有明确目标玩家的剧情、招募等角色内容，读取当前查看者为该角色保存的装扮。
- 对局开始时把双方当前角色服装标识与立绘地址写入对局/回放快照；旧回放不随玩家之后换装而改变。
- 彩虹豆豆跳跳糖等临时立绘效果优先于已装备服装；效果结束后恢复玩家原先装备的服装。
- 后续每件服装可拥有用户手动提供的专属糖果特效立绘；当前五件服装尚未提供这些变体。
- MVP 只支持“一件服装替换整张角色立绘”，不预建稀有度、限时售卖、赠送、第二货币或多部位叠穿模型。
- 服务端权威校验金币、服装存在性、购买资格、重复购买与对应角色。
- 用户拥有服装和各角色当前装扮必须持久化，刷新或重新登录后保持。

- 玩家端深红戏剧服装店使用响应式分层 CSS 场景；移动端单独按竖屏重排，切换与状态动效提供 reduced-motion 退化。

- 残星会接待区与扎希拉商铺复用同一个钱包组件、钱包 WebP、金币胶囊与文字排版；只允许因两店布局不同而调整定位。

## Decisions (ADR-lite, evolving)

### 未拥有角色时的服装展示与购买

**Context**：完全隐藏会让玩家不知道有哪些服装，允许提前购买又可能造成无法立即使用的误购。

**Decision**：未拥有对应角色时仍展示服装，但服装立绘使用灰色锁定态；允许查看详情，不允许购买。

**Consequences**：商品池过滤必须区分“服装已拥有”和“对应角色未拥有”；购买接口必须权威校验角色所有权，详情需要提供明确的锁定原因。

### 玩家换装的立绘生效范围

**Context**：玩家希望换装相当于完整替换角色立绘，而不是仅改变部员手册或对局中的局部头像。

**Decision**：装备服装在该角色于玩家端出现的所有立绘位置全局生效，包括剧情和招募；多人界面按目标玩家的装扮展示，无目标玩家的内容按当前查看者保存的装扮展示。

**Consequences**：用户装扮选择必须进入玩家公开 payload、房间/观战/结算/资料链路，并为回放定义稳定语义；剧情、招募及其他所有角色立绘消费者也必须改用统一的装扮解析入口，不能继续直接读取角色目录原画。

### 店面切换时的商品与冷却状态

**Context**：如果切换店面会重新随机商品，玩家可以用切换绕过刷新规则；如果共用冷却，两个独立店面会互相阻塞。

**Decision**：扎希拉商铺和残星会在同一次窗口会话中各自保存当前批次、下一预加载批次和独立刷新冷却；关闭整个商店后，下次打开重新生成。

**Consequences**：商店窗口需要同时挂载或保留两个独立目录会话状态，平移动效只能改变可见店面，不能触发重新取批；关闭窗口时统一释放预加载、计时器与临时状态。

### 回放服装的时间语义

**Context**：如果历史回放读取玩家当前服装，同一回放会在玩家换装后改变画面，无法准确保留对局当时的外观。

**Decision**：对局开始时快照双方当前角色的服装标识与立绘地址；即时观战、结算和历史回放均使用该局快照。

**Consequences**：房间玩家视图、持久化房间状态、对局记录和回放 payload 都需要携带服装快照；恢复或回放时不得回查玩家当前装备来覆盖历史值。

### 服装详情的信息密度

**Context**：商品卡按参考图保持“立绘 + 售价”的轻量展示，购买操作必须移入详情，因此详情需要承载完整决策信息。

**Decision**：详情展示服装大图、服装名、所属角色、简短介绍、插画署名、原价/折扣价、持有或锁定状态和购买按钮；不增加默认立绘对比切换。

**Consequences**：服装数据需要具备独立名称、角色归属、描述、立绘、署名和定价字段；可以复用现有商店署名规范，但购买按钮与状态校验需要服装专属语义。

### 购买成功后的商品与装备状态

**Context**：购买后立即移除卡片会改变参考图布局，默认自动装备又可能覆盖玩家正在使用的造型；但刚购买时提供一次快捷装备可以减少操作路径。

**Decision**：购买成功后详情保持打开并显示“已拥有”，卡片保留至下一次手动刷新，娜波摩显示感谢台词；随后询问是否装备，确认则立即保存，取消则只授予所有权。

**Consequences**：购买与装备是两个独立的服务端写操作和失败边界；购买成功但装备失败时不得回滚所有权或金币，只提示装备失败并允许玩家之后在部员手册重试。

### 部员手册换装的提交时机

**Context**：原始设想包含独立保存按钮；进一步确认后，服装卡片本身还需要承担查看详情，不能把整张卡片同时作为换装写操作。

**Decision**：点击服装卡片只打开详情；点击卡片内独立的衣服图标按钮才立即持久化并全局生效；换装弹窗不提供额外保存按钮。

**Consequences**：卡片主体与装扮按钮必须是独立、可键盘操作且不会事件串扰的交互目标；装扮按钮需要提交中状态、防重复点击、失败回滚和明确选中态。

### 换装弹窗的目录与卡片结构

**Context**：只展示已拥有服装会让玩家无法从角色详情发现未解锁造型，也无法查看其详情。

**Decision**：衣服按钮始终可点击，弹窗展示该角色全部服装；未拥有卡片灰化但可查看详情，装扮按钮禁用；整体操作仿照部员手册角色卡片的“卡片详情 + 独立出战按钮”。

**Consequences**：玩家端需要获得所有启用服装的公开目录以及当前用户所有权，灰化只影响立绘和装扮资格，不能让详情按钮失去可访问性；服务端装备接口仍需拒绝未拥有服装。

### 默认立绘在服装目录中的表示

**Context**：玩家需要稳定、可发现的方式换回角色默认立绘，且换回操作应与其他服装保持一致。

**Decision**：每个角色的默认立绘作为永久拥有的“默认服装”卡片，固定排在该角色服装目录第一张；卡片可查看详情，装扮按钮可随时使用。

**Consequences**：默认服装不需要购买记录，但要在目录 payload 中作为稳定的虚拟条目出现；装备存储可用空值或明确默认标识，接口和客户端必须统一处理。

### 娜波摩看板娘素材

**Context**：仓库默认娜波摩立绘是正面站姿，参考布局需要挥手的店铺看板娘造型。

**Decision**：使用用户提供的三张 1000×1000 透明 PNG 作为闲置、购买成功、刷新/空商品/金币不足状态源图，实施时转换为保留透明通道的 WebP 并放入项目资源目录。

**Consequences**：运行时、预加载清单和测试只引用项目内 WebP；仓库外 PNG 只作为一次性源素材，转换时不得合成白底或破坏透明边缘。

### 娜波摩状态反馈

**Context**：服装店需要让刷新、购买成功、空目录和购买失败在聊天框与角色表情上都可辨识。

**Decision**：闲置进店使用挥手图和随机问候；购买成功使用“谢谢惠顾”图；刷新、空商品和金币不足使用“空或刷新”图，其中金币不足固定台词为“你是来找茬的吧？”。

**Consequences**：看板娘状态机必须区分余额不足与其他购买错误，图片和台词需要同步切换；状态不能只靠颜色表达，并要为图片加载失败保留文字反馈。

### 残星会店内视觉场景

**Context**：参考图中的绿色只是布局占位，正式界面需要与残星会 cosplay 服装店和娜波摩看板娘形成明确场景。

**Decision**：采用稍阴暗的戏剧舞台服装店方向，以深红/酒红为主，结合暗色幕布、暖色局部灯光与少量旧金色舞台细节。

**Consequences**：背景应使用可响应桌面和竖屏的分层场景构图，装饰保持在边缘和负空间；商品、价格标签、聊天框、钱包和按钮必须有独立高对比承载面，并满足键盘焦点与禁用态可辨识性。

### 首批服装商品与资源规范

**Context**：首版需要真实商品验证购买、灰化、详情、换装与全局立绘链路；五张源图存在 800×800 与 1000×1000 两种画布尺寸。

**Decision**：内置西格莉卡 1 件、达妮娅 2 件、娜波摩 2 件，共五件服装，初始售价均为 600 金币；实施时统一透明有效内容的视觉占比并输出稳定方形 WebP。

**Consequences**：默认快照需要保存五件服装及其可后台编辑字段；资源处理必须以透明内容边界为准，不得简单拉伸 800×800 源图或合成白底。

### 后台服装管理入口

**Context**：服装同时具有角色归属、全局立绘和换装语义，若混入普通商品表单会增加无关字段和条件分支。

**Decision**：后台新增独立“服装管理”页，集中维护服装标识、名称、所属角色、立绘、简介、插画署名、售价/折扣、显示、购买状态和排序。

**Consequences**：服装模型与管理 API 应形成独立领域入口，但购买事务、金币规则、审计和默认快照继续复用现有商业基础设施；后台管理界面按项目约定无需移动端适配。

### 停用服装对已购用户的影响

**Context**：后台需要能紧急撤下错误或不适合继续展示的服装，同时避免停用操作破坏金币购买历史。

**Decision**：服装停用后对所有玩家不可装扮，当前装备者自动回退默认立绘；购买所有权记录保留，重新启用后恢复使用资格。

**Consequences**：装备接口与所有立绘解析必须校验服装当前启用状态；用户 payload 发现已装备服装失效时应权威回退并持久化默认值。后台删除应优先使用停用/归档语义，不能级联删除购买历史。

### 商店批次中锁定服装的优先级

**Context**：未拥有角色的服装需要可见以供预览，但如果与可购买服装等概率随机，玩家可能连续得到无法购买的整批商品。

**Decision**：每批先从玩家已拥有角色的未购服装中随机选择，不足五件时再用未拥有角色的灰色锁定服装补满。

**Consequences**：批次算法需要按购买资格分层洗牌，同时继续优先避开上一批商品；锁定服装是补位候选，不会挤掉当前可购买服装。

### 换装目录的扩展布局

**Context**：首版每个角色只有少量服装，但独立服装管理会持续增加内容，不应以首屏数量限制数据模型。

**Decision**：换装弹窗采用不限数量的响应式网格滚动，桌面多列、竖屏手机两列，标题和关闭按钮保持可见，不分页。

**Consequences**：列表区域承担局部滚动并保留键盘焦点可见性；服装图片需要懒加载或有界预加载，避免未来目录增长后一次解码全部大图。

### 服装与临时糖果立绘效果的优先级

**Context**：现有彩虹豆豆跳跳糖通过角色级立绘替换表达玩法状态，而首批服装尚无逐件对应的糖果效果图。

**Decision**：当前临时糖果立绘效果优先于服装；效果结束后恢复玩家此前装备的服装。未来由用户逐件提供服装专属糖果效果图。

**Consequences**：统一立绘解析顺序必须是“有效的临时效果变体 → 有效的装备服装 → 角色默认立绘”；临时效果不能改写或清空装备记录，未来数据模型应能为服装挂接可选效果变体。

### 服装专属糖果特效扩展点

**Context**：用户计划后续逐件提供服装专属糖果特效图，若当前模型完全不留入口，后续需要再次迁移数据库和重做后台表单。

**Decision**：当前服装模型和独立后台管理页增加可选糖果特效立绘字段；首批五件暂不配置，使用角色级糖果立绘回退。

**Consequences**：立绘解析在糖果效果激活时先检查当前服装的有效变体，再回退角色级效果；字段需要通过默认快照、后台 API 和玩家目录安全传递，但空值不增加首版素材要求。

### 后台服装素材录入方式

**Context**：现有后台内容以资源路径/URL 管理图片；增加文件上传会引入部署持久化、文件校验、清理和安全边界。

**Decision**：普通服装立绘和可选糖果特效立绘均填写项目资源路径或受支持 URL，不在当前任务中建设上传系统。

**Consequences**：管理员需要先把素材部署到稳定地址；后台和服务端沿用现有站内路径/http(s) 校验，玩家端只接收归一化后的安全资源地址。

### 首批服装初始名称

**Context**：源文件名是日文工作文件名，直接显示会泄露素材管理细节；当前也没有确认正式服装设定名。

**Decision**：首批使用角色名加编号的中性名称：西格莉卡 01、达妮娅 01/02、娜波摩 01/02。

**Consequences**：默认快照提供稳定非空名称；正式命名不阻塞首版，管理员之后可从服装管理修改，玩家端不得把源文件名当作回退文案。

### 部员手册服装详情的购买边界

**Context**：部员手册会展示完整服装目录；若允许直接购买，将绕过残星会的随机五件、刷新冷却和店面体验。

**Decision**：部员手册详情仅用于预览、状态与价格查看，不允许直接购买；购买只在残星会当前批次的商品详情中发生。

**Consequences**：服装详情组件需要明确区分“衣柜预览上下文”和“服装店购买上下文”；前者不得渲染或调用购买操作，服务端购买仍只接受有效店面商品。

### 部员手册到服装店的导航边界

**Context**：完整服装目录可以自然引导商店，但自动跳转会打断部员手册的浏览上下文，也无法保证目标服装出现在当前随机批次。

**Decision**：部员手册服装详情不提供“前往残星会”按钮或提示，仅展示信息与未拥有状态。

**Consequences**：服装店继续只有首页商店窗口内的切换入口；部员手册不需要跨 overlay 导航或共享当前服装店批次。

### 商店窗口的默认店面

**Context**：现有首页只有一个商店入口；记忆店面或增加第二入口都会改变当前用户路径。

**Decision**：每次打开商店窗口始终先显示扎希拉商铺，玩家再通过窗口内“← 残星会”切换。

**Consequences**：当前店面只需会话内状态；关闭窗口后重置为扎希拉，不写本地或服务端偏好，也不修改首页入口布局。

### 未拥有角色时的服装目录操作

**Context**：衣服按钮始终可点击用于浏览完整目录，但玩家不应为尚未拥有的角色保存装扮。

**Decision**：未拥有角色时允许浏览所有服装和详情，所有装扮按钮直接禁用，不提供额外提示；默认服装卡不灰化，未拥有的其他服装照常灰化。

**Consequences**：装扮资格同时要求角色所有权和服装所有权；禁用按钮仍需保留原生 disabled 语义与清晰视觉状态，但不得触发 toast、tooltip 或聊天框反馈。

### 后台服装状态语义

**Context**：内容运营需要分别控制商店曝光、新购买和紧急停止使用，单一启用开关无法覆盖这三种场景。

**Decision**：“商店显示”仅控制残星会商品池；“可购买”仅控制新购买；“停用”控制全局装扮资格并让当前装备者回退默认。所有权记录在三种操作下均不删除。

**Consequences**：目录与购买接口必须分别校验 `shopVisible`、`purchasable` 和 `enabled`；部员手册完整目录忽略 `shopVisible`，已拥有者使用不可购买服装不受影响，但任何停用服装都不可装备。

### 部员手册服装目录排序

**Context**：目录同时承担快速换装和未拥有服装预览，完全按后台排序会让当前装扮与已拥有服装被锁定商品淹没。

**Decision**：默认服装固定第一；当前装扮若非默认则紧随其后；剩余已拥有服装在前、未拥有服装在后，各组内部按后台排序。

**Consequences**：排序是当前用户派生视图，不能回写后台 `sortOrder`；当前装扮状态变化后列表需要稳定重排并保持合理滚动位置。
