# 商店窗口与商品刷新系统重构

## Goal

重构桌面端与移动端的玩家商店，把现有分类选项卡和分页商品网格改为最多展示 5 种商品的单一陈列区，并围绕刷新商品、用户可购买性、钱包、扎希拉立绘与台词重新建立清晰且有角色感的响应式布局。

## What I already know

- 用户要求先创建分支、审查现有系统，并通过 grill-me 收敛需求；当前阶段只做规划，不写商店实现代码。
- 已创建分支 `codex/shop-window-redesign`，从原工作分支 HEAD 建立并保留原有未提交 WIP，不会把无关改动混入本任务。
- 桌面与移动端均取消分类选项卡，所有商品进入同一个候选池。
- 商品区最多显示 5 种商品；少于 5 种时只使用真实商品并自适应填充。
- 对当前用户已售罄的商品不再显示。
- 刷新后优先出现上一批未出现的商品。
- 商品卡片需要自适应分布，并具有受控的随机旋转与上下浮动效果。
- Header 从左到右是刷新按钮、标题、关闭按钮。
- 桌面草图：商品区在左侧主体，钱包在左下，扎希拉立绘在右下，台词在立绘上方并允许覆盖部分 header 背景，但不能覆盖立绘、商品区或关闭按钮。
- 移动草图：商品区在上半部，台词与钱包位于商品区下方，扎希拉立绘锚定底部。
- 当前 API 一次返回全部启用商品，前端按分类和每页 8 个切页；服务端没有“当前 5 件商品”或刷新历史状态。
- 当前本地数据库与持久化默认快照均为 6 个启用商品：杂物 3、装饰 2、音乐 1。
- 当前库存上限是按用户累计购买次数计算，而非全服共享库存。
- 当前卡片点击主体打开商品详情，点击购买按钮直接购买；购买成功后扎希拉切换为感谢台词和立绘 5 秒。
- 现有 Bright School 商店样式跨 base、theme、component repair、mobile 和 final override 多层，且已有桌面/移动端结构测试与 CSS 契约。

## Design Brief

- **Feature summary**: 面向登录玩家的生产级商店整体重构；取消分类与分页，把浏览、刷新、查看详情和购买集中到一个最多 5 件商品的角色化陈列窗口。
- **Primary action**: 玩家快速判断当前可购买商品，并直接购买或刷新下一批；扎希拉、钱包和台词提供状态解释与场景氛围，但不能妨碍商品操作。
- **Visual direction**: 保留 Bright School 明亮纸张/校园手账身份，采用克制底色与角色/商品作为重点。场景句：玩家在明亮的校园商铺摊位前轻松挑选商品，扎希拉在右下方接待并随操作回应。主要参考为用户桌面草图、移动草图和现有 Bright School/Zahira 运行时资产。
- **Scope**: 桌面与移动端完整商店表面、生产级交互、响应式布局、钱包新资产、状态反馈、测试和系统设计文档；不是仅供预览的原型。
- **Desktop layout**: Header 顶部固定刷新/标题/关闭；商品区位于左侧主体并按五件 2+3、四件 2+2、三件 2+1、一至两件单排居中的数量拓扑排列，随机位置扰动只能发生在不碰撞的安全槽位内；钱包左下；扎希拉右下；台词贴近立绘上方，不得遮挡商品、立绘或关闭按钮。
- **Mobile layout**: Header 顶部固定；商品区在上半部使用无内部滚动的 2+3 构图；台词与钱包位于商品区下方；扎希拉锚定底部并按空间裁切。极端尺寸优先整卡同比缩放，允许卡片内部控件低于 44px，header 主控件不缩小。
- **Key states**: 加载、目录失败/重试、3 秒冷却、可刷新、零候选、1–4 件候选、购买中、金币不足、购买成功、已拥有和已售罄短暂保留、图片预加载失败、减少动态。
- **Interaction model**: 卡片主体打开独立详情，购买按钮直接购买；刷新消费预备批次并以轻量交叉淡变切换；关闭和键盘路径始终可用。
- **Content and asset requirements**: 标题“扎希拉商铺”；精确加载、失败、感谢和空状态台词；新增 4:3、1024×768、透明 Bright School 手账贴纸风钱包资源，通过共享常量替换。
- **Implementation references**: 实施阶段优先参考 Impeccable `layout`、`adapt`、`animate`、`harden` 规范和 `interaction-design`；钱包资源遵循 `imagegen` 的项目绑定透明资产流程。

## Requirements

- 移除玩家商店的分类选项卡和传统分页入口。
- 单一商品陈列区最多展示 5 个符合当前用户条件的商品。
- 对当前用户已售罄的商品不得进入陈列候选池。
- 用户已拥有的角色、装饰、音乐等一次性商品不得进入候选池；可重复购买的消耗品即使当前已持有仍可出现，直至达到该用户购买上限。
- 购买成功后不自动刷新或补位：若该商品变为已拥有或已售罄，当前卡片保留并切换为对应禁用状态，直至用户手动刷新；仍可重复购买的消耗品则更新剩余库存并保持可购买状态。
- 刷新不消耗金币或次数，但每次成功刷新后进入 3 秒商店窗口会话级客户端冷却；冷却期间刷新按钮不可重复触发，关闭商店后冷却状态重置。
- 当前批次出现后，在 3 秒冷却期间立即确定下一批商品并预加载该批商品图像；冷却结束后点击刷新直接提交已准备批次，不在点击时临时抽样或等待图片加载。
- 首次打开商店并显示初始批次时同样立即进入 3 秒准备冷却，在此期间确定并预加载第二批；首次手动刷新不走特殊即时路径。
- 冷却期间刷新按钮保持原位并禁用，在按钮内部显示圆形进度环与 `3 / 2 / 1` 秒数字；可访问名称同步说明剩余时间，冷却结束恢复刷新图标和可操作状态。
- `prefers-reduced-motion: reduce` 下不播放进度环连续旋转，只保留离散数字变化和最终状态切换。
- 每张商品卡进入当前批次时生成并记录一个约 `-2deg` 到 `2deg` 的初始随机角度；该角度在卡片留在当前批次期间固定不变，不参与动画。
- 只有垂直位移参与持续动效：上下浮动总幅度约 `4–6px`、周期约 `5–8 秒`，各卡片使用错开的相位/周期，避免整齐同步。
- 卡片悬停、键盘聚焦、按下和购买操作期间暂停浮动；`prefers-reduced-motion: reduce` 下完全取消浮动但保留固定初始角度。
- 移动端常规竖屏的 5 件商品按草图使用上排 2 张、下排 3 张；少于 5 张时按真实数量居中、自适应填充。
- 移动端商品区不允许内部滚动，也不把第 5 张商品推入可滚动第三行；空间不足时对整张卡片及其图片、文字、价格和购买按钮做一致比例缩放，允许卡片内部触控控件低于 44px。
- 移动端整卡缩放不设置固定像素下限；在极端窄屏/矮屏上继续同比缩小，以完整保留单屏构图、全部真实商品卡和非滚动商品区为最高优先级。
- 扎希拉台词按事件变化：首次打开从欢迎语池随机选择；每次手动刷新从刷新语池选择；购买成功使用现有 `谢谢惠顾！` 并切换感谢立绘 5 秒；候选为 0 时使用专用空状态台词。
- 购买成功台词和感谢立绘在 5 秒内临时覆盖当前欢迎/刷新场景台词，计时结束后恢复最新场景台词；冷却倒计时本身不改变台词。
- 候选商品为 0 时商品区保持完全空白，不显示空状态标题、说明、图标或伪商品卡；扎希拉固定显示台词“还在进货中哦，请下次再来吧。”，刷新按钮使用灰色禁用状态。
- 1–4 个候选商品时只渲染真实卡片并按数量居中、自适应填充，不出现空槽位。
- 商品卡表面保留商品图片、名称、价格、购买按钮和消耗品库存信息；有限消耗品显示当前用户剩余库存，不限量消耗品显示“不限量”。
- 角色、装饰和音乐等一次性商品不显示“限购 1”占位行；折扣商品继续同时显示划线原价和最终价格。
- 沿用现有详情交互：点击卡片非购买区域或在卡片主体上按 Enter/Space 打开独立商品详情窗口；点击购买按钮直接购买并阻止卡片点击冒泡，不先打开详情。
- 详情窗口继续展示商品图片、类别、名称、介绍、插画署名和持有状态，且保持独立关闭与键盘交互。
- 桌面端商品卡按数量使用平衡行拓扑，槽位内位置按批次种子轻微扰动并进行真实卡片边界安全约束；卡片之间不得重叠，也不得越出商品区或侵入 header、扎希拉、台词、钱包和关闭按钮安全区。
- 桌面随机位置与固定随机角度在当前批次生成时一次确定，当前批次内不因渲染、购买或浮动动画重新排布；下一批的位置可在 3 秒冷却期间连同商品一起预先生成。
- 碰撞检测需要为 `±2°` 旋转和 `4–6px` 浮动预留安全间距；若当前卡片尺寸无法完成无碰撞放置，则按可用空间统一缩小卡片后重新随机，而不是允许重叠。
- 桌面键盘焦点顺序按最终视觉位置从上到下、从左到右排列，避免随机 DOM 顺序与屏幕位置不一致；移动端仍使用已确认的稳定 2+3 构图，仅角度随机。
- 手动刷新消费预备批次时采用约 `220ms` 的轻量交叉淡入淡出：旧卡淡出，新卡在预生成位置以约 `4px` 的轻微垂直位移淡入；不使用飞出、弹跳或长时间编排。
- 换批过渡不得阻塞关闭按钮等窗口级操作；`prefers-reduced-motion: reduce` 下改为极短透明度切换或即时替换。
- Header 正式标题固定为“扎希拉商铺”；从左到右依次为刷新按钮、标题和关闭按钮，并为窗口建立匹配标题的对话框可访问名称。
- 首次目录加载时商品区保持空白，不渲染骨架卡或“加载中”行内文字；扎希拉显示“稍等一下，我正在整理商品哦。”，刷新按钮禁用。
- 目录请求失败时商品区继续保持空白，扎希拉显示“进货单好像出了点问题，请再试一次吧。”，保留现有错误 toast；header 刷新按钮退出冷却语义并变为可操作的重试入口。
- 重试成功后按正常初始批次流程生成商品、启动 3 秒冷却并准备第二批；重试期间按钮再次禁用，失败时仍可继续重试。
- 钱包区域不复用 `gacha-coin-bag.svg` 或当前 Lucide `CircleDollarSign`，而是新增“扎希拉商铺”专用钱包图片，并在图片旁显示当前用户金币数量。
- 新钱包图片作为项目运行时资产交付，需要适合透明背景、桌面左下与移动端钱包位置的同比缩放，不包含烘焙文字、水印或固定金币数。
- 初版钱包图片采用 Bright School 手账贴纸风格：扁平钱包/零钱包主体、深色手绘感轮廓、纸张贴纸质感和简化高光，与现有校园手账界面协调，不采用写实立体道具或木质钱匣方向。
- 钱包资源必须保留后续由用户替换图片的明确入口；组件不得把生成图以 data URL、内联 SVG 或分散 CSS URL 写死。
- 钱包运行时路径通过共享商店资源常量（例如 `SHOP_WALLET_IMAGE`）集中维护；后续替换时新增版本化图片并只修改该常量，不要求改动钱包组件或覆盖同名文件。
- 钱包透明母版固定为 4:3、1024×768；主体采用横向贴纸构图并保留透明安全边距，运行时使用 `object-fit: contain` 同比缩放，金币数量不烘焙进图片。
- 完整商品目录仅在打开商店或目录错误重试时请求；商店打开期间的手动刷新只消费本地预备批次，不重新请求服务端目录。
- 若冷却期间购买行为改变用户拥有状态或剩余库存，必须按最新用户状态重算下一批并预加载新加入的替代商品，避免下一次刷新展示已拥有或已售罄商品。
- 下一批图像预加载采用尽力而为和有界失败策略：图片失败不得永久锁住刷新按钮；现有登录预加载仍负责全量商店图片，本地批次预加载作为下一轮展示的定向保障。
- 刷新历史仅存在于本次商店窗口的打开期间；关闭并重新打开商店后重置，不写入浏览器持久化存储或服务端账号数据。
- 手动刷新只比较当前批次与紧邻的上一批：先放入上一批未展示的合格商品，再从上一批商品中随机补满，且同一批内不重复。
- 少于 5 个候选商品时使用真实数量自适应布局，不显示伪造的空商品卡。
- 桌面和移动端提供等价的刷新、查看详情、购买、关闭与钱包信息能力。
- Header 顺序固定为刷新、商店标题、关闭。
- 随机旋转/浮动不得破坏可读性、命中区域、键盘焦点、卡片间距或减少动态偏好。
- 扎希拉立绘、台词、钱包和商品区按草图建立明确的不重叠安全区。
- 保留服务端购买事务、金币扣除、资产发放、库存/拥有校验和成就触发的正确性。

## Acceptance Criteria

- [ ] 桌面与移动端均不再显示分类选项卡和页码。
- [ ] 任意时刻最多渲染 5 张真实商品卡；候选少于 5 个时无空占位卡。
- [ ] 当前用户已售罄的有限道具不会显示，也无法通过旧状态发起有效购买。
- [ ] 当前用户已拥有的一次性商品不会显示；尚可重复购买的消耗品不会仅因已持有而被隐藏。
- [ ] 购买后当前批次和卡片位置保持稳定；变为不合格的卡片显示禁用结果状态，并仅在下一次手动刷新时从陈列中移除。
- [ ] 刷新免费且不限总次数；冷却期间重复点击或键盘触发不会生成新批次，关闭重开后不保留冷却。
- [ ] 每次刷新后的 3 秒内会稳定生成且只生成一份下一批结果，并发起下一批图像预加载；冷却后点击展示该预备结果。
- [ ] 初始批次出现后刷新按钮立即进入 3 秒冷却，首次可用时已经存在预备第二批。
- [ ] 冷却按钮显示内嵌进度环和 `3 / 2 / 1`，不改变 header 占宽；辅助技术能获得剩余时间，减少动态模式无连续旋转。
- [ ] 冷却期间发生购买时，预备批次会按最新拥有/库存状态失效重算；预加载失败不会造成刷新永久不可用。
- [ ] 同一次商店打开期间，刷新后的批次优先选择紧邻上一批未出现的商品且批内无重复；关闭重开后不沿用历史。
- [ ] 购买与用户金币/资产更新仍由现有服务端事务保障。
- [ ] 桌面布局满足 header、左侧商品区、左下钱包、右下扎希拉和安全台词区约束。
- [ ] 移动布局满足草图的信息顺序，并在典型窄屏和矮屏上无横向溢出或关键控件遮挡。
- [ ] 移动端 5 张卡默认保持 2+3 构图且商品区无内部滚动；窄屏/矮屏通过整卡等比缩放适配，少于 5 张时居中重排。
- [ ] 移动商品卡缩放没有硬编码的按钮或字体最小像素值；在目标最小视口上仍完整显示全部卡片且不产生商品区滚动或横向溢出。
- [ ] 打开、刷新、购买成功和空候选分别触发对应台词；购买感谢状态持续 5 秒并在结束后恢复最新场景上下文，冷却期间不重复切换台词。
- [ ] 零候选时商品区完全空白、无空状态文字或占位卡，扎希拉显示精确台词“还在进货中哦，请下次再来吧。”，刷新按钮灰显且不可操作。
- [ ] 1–4 个候选时仅显示对应数量的真实商品卡并居中重排。
- [ ] 桌面和移动卡片均显示图片、名称、价格、购买按钮及适用的消耗品库存；一次性商品不显示无意义的限购文案。
- [ ] 卡片主体支持鼠标与键盘打开独立详情，购买按钮直接购买且不会同时打开详情；详情窗口原有内容和关闭路径保留。
- [ ] 桌面每批卡片位置完全随机但无重叠、无越界，并为旋转/浮动留出安全间距；布局在当前批次内稳定，键盘顺序匹配视觉顺序。
- [ ] 桌面随机放置空间不足时统一缩小后重试，不能以卡片互相覆盖作为降级；移动端不使用随机位置。
- [ ] 刷新换批以约 220ms 交叉淡入淡出和最多 4px 位移完成，期间关闭操作可用；减少动态模式无位移动画。
- [ ] 桌面和移动 header 均以“扎希拉商铺”为标题，并保持刷新、标题、关闭的从左到右顺序和可访问名称。
- [ ] 加载和失败状态的商品区均无骨架或行内文字；扎希拉显示精确加载/失败台词，失败 toast 保留，刷新按钮在失败态可重试且成功后恢复正常批次冷却流程。
- [ ] 钱包区域使用新生成并纳入项目的专用透明背景图片，旁边显示实时金币数；不再使用现有金币袋 SVG 或 Lucide 圆形金币图标。
- [ ] 初版钱包为 Bright School 手账贴纸风透明位图，且替换入口集中、可记录，不需要重写钱包组件布局。
- [ ] 钱包组件只消费共享资源常量；替换为新文件时修改单一配置即可，且支持通过版本化文件名规避浏览器旧缓存。
- [ ] 钱包母版为 1024×768 透明 4:3 资源，桌面和移动端均完整显示主体且不拉伸，金币数字保持独立实时文本。
- [ ] 手动刷新不产生新的 `/api/shop` 请求；关闭重开或错误重试会重新拉取目录，后台商品变更在下一次重新拉取后生效。
- [ ] 卡片随机姿态可测试、可复现或被约束，且 reduced-motion 下无持续漂浮。
- [ ] 同一批次内每张卡的随机角度保持固定且限制在约 `±2°`；只有 `4–6px` 垂直浮动是持续动画，交互态与 reduced-motion 下停止。
- [ ] 加载、失败、0–4 个候选、购买中、金币不足和成功购买状态都有明确反馈。
- [ ] 更新相关组件/服务测试、CSS/主题契约和系统设计文档，并运行 `npm run docs:system-design`。
- [ ] `npm run check` 通过，或明确区分与本任务无关的既有失败。

## Technical Approach

- 保持现有 `GET /api/shop` 与购买事务协议不变；目录在打开/错误重试时加载，商品选择、会话刷新历史、冷却和预备批次均为前端窗口级状态。
- 从 `shopModalHelpers.js` 拆出可注入随机源的纯函数：合格候选过滤、最多 5 件抽样、上一批差集优先、固定角度/浮动参数生成、桌面无碰撞放置和视觉顺序排序。
- 使用显式状态机或等价单向状态组合区分 `loading`、`error`、`empty`、`cooldown`、`ready` 和 `transitioning`，避免刷新按钮、扎希拉台词与预备批次出现互相覆盖的布尔状态。
- 当前批次确定后立刻生成下一批商品、桌面位置和动画参数，并通过现有预加载模块暴露的有界图片加载能力定向预热；购买成功或资格变化会让预备批次失效重算。
- 桌面商品区尺寸变化时保留当前商品与批次种子，只在数量拓扑的安全槽位内重新计算坐标扰动和必要缩放；移动端复用相同数量拓扑但不使用随机位置。
- 将固定旋转层、浮动层和 220ms 批次过渡层分离，避免多个效果争用同一个 `transform`；所有持续动画使用 transform/opacity 并提供 reduced-motion 路径。
- 重构 `ShopSidebar` 为扎希拉舞台、台词和钱包的响应式组合；钱包资源常量集中在共享商店资产模块，并加入运行时商店图片预加载清单。
- 钱包先生成 1024×768 透明 PNG 母版，再输出项目运行时透明 WebP；保留母版，组件只引用共享版本化路径常量。
- 清理已废弃的分类 tab、分页、8 个空槽与相关 CSS/HUD 契约；更新 base、Bright School、component repair、mobile 和 final override 层，避免旧 `!important` 重新覆盖新布局。
- 更新 `ShopModal.test.js`、helper/hook 测试、预加载测试、样式/主题契约和必要的服务端回归测试；对桌面随机算法使用确定随机源，对典型与极端移动视口进行浏览器视觉验证。

## Decision (ADR-lite)

**Context**: 现有服务端只返回完整启用商品目录，没有当前展示批次或刷新历史状态；当前需求只要求刷新时优先展示前一批未出现商品。

**Decision**: 刷新历史采用商店窗口会话级前端状态。每次刷新仅以紧邻上一批为排除优先级，关闭商店即清空。

**Consequences**: 无需新增数据库字段、服务端接口或本地持久化；跨窗口和跨设备不保证批次连续性。当前 6 个候选、每批 5 个时，刷新最多引入 1 个新商品，其余位置从上一批随机补足。

### Eligible product pool

**Context**: 新商品区只有 5 个展示位，继续展示已拥有且不可重复购买的商品会挤占有效购买机会；消耗品则允许重复购买。

**Decision**: 候选池排除当前用户已拥有的一次性角色、装饰和音乐，以及当前用户已售罄的有限消耗品；仍可购买的消耗品不因已有库存而隐藏。

**Consequences**: 不同用户看到的候选数量可能不同，商品不足 5 个时布局必须按真实数量收缩并重新分布。

### Post-purchase display

**Context**: 购买一次性商品或买完有限库存后，该商品已不再符合后续候选条件，但立即移除或整批刷新会让用户失去明确的购买成功落点。

**Decision**: 当前卡片保留到下一次手动刷新，并显示 `已拥有` 或 `已售罄` 禁用状态；不自动补位、不移动其余卡片。仍可重复购买的消耗品只更新库存并继续可购买。

**Consequences**: “隐藏不合格商品”约束作用于初次生成和手动刷新候选池；刚刚购买成功的当前卡片是短暂例外，提供稳定的结果反馈。

### Refresh cost and cooldown

**Context**: 用户希望允许反复刷新商品，但需要避免快速连续触发造成卡片高频闪动和状态难以辨认。

**Decision**: 刷新免费且无总次数限制；每次成功刷新后采用 3 秒客户端冷却。冷却仅存在于当前打开的商店窗口，不新增服务端经济或防刷状态。

**Consequences**: 关闭并重开商店可重置冷却，因此该机制是交互节奏保护而不是经济约束；按钮使用已确认的内嵌进度环和数字倒计时反馈。

### Prepared next batch

**Context**: 当前登录启动流程已经通过 `loginPreloadAssets()` 把完整商店目录图片加入延迟预加载，但该过程允许超时跳过并异步重试；用户希望刷新点击本身不再承担抽样和资源加载成本。

**Decision**: 每次当前批次确定后，立即按“优先上一批未出现商品”的规则生成下一批，并在 3 秒冷却窗口内定向预加载其图像。刷新提交预备批次后，再为后续一轮重复该过程。

**Consequences**: 下一批选择在冷却期间稳定，不会因点击时重新随机而变化；购买导致拥有/售罄条件改变时必须让预备批次失效并重算。预加载是有界、可失败的性能优化，不改变服务端购买校验，也不能永久阻塞刷新。

### Initial shop opening

**Context**: 如果首次打开商店后立即允许刷新，第二批可能尚未完成定向预加载，与后续刷新体验不一致。

**Decision**: 初始批次视为本次窗口会话的第一批；显示后立刻开始 3 秒冷却、生成并预加载第二批。

**Consequences**: 用户首次打开后需要等待最多 3 秒才能刷新，但所有手动刷新都统一消费已准备批次，不存在首次刷新特例。

### Cooldown feedback

**Context**: 仅将刷新按钮变灰无法说明何时可再次使用，而外置倒计时会改变 header 宽度并挤压标题和关闭按钮。

**Decision**: 在固定尺寸刷新按钮内部显示圆形进度环和 `3 / 2 / 1` 数字倒计时，并更新可访问名称；减少动态模式只显示离散数字。

**Consequences**: Header 布局保持稳定，用户能预测等待时间；实现需要覆盖普通、冷却、键盘焦点和 reduced-motion 状态。

### Product card motion

**Context**: 商品陈列需要有轻微、各不相同的手工摆放感，但旋转持续变化会让文字、价格和购买按钮难以稳定阅读。

**Decision**: 卡片进入当前批次时生成约 `±2°` 的固定随机旋转；只有 `4–6px`、`5–8 秒`、错相位的上下浮动持续播放。交互态暂停浮动，减少动态模式完全禁用浮动。

**Consequences**: 每次切换到新批次时可获得新的陈列姿态，当前批次内内容和命中区域保持稳定；实现应分离固定旋转层与浮动动画层，避免 transform 相互覆盖。

### Mobile card composition

**Context**: 草图把 5 张商品卡组织为 2+3 两排，并要求扎希拉、台词和钱包同时保留在单个移动端商店窗口内；内部滚动会破坏这一整体构图。

**Decision**: 移动商品区禁止内部滚动，5 张卡固定使用 2+3 构图；空间不足时整卡及全部内容一致缩放，允许购买控件低于通常的 44px 触控基线。少于 5 张时按数量居中重排。

**Consequences**: 构图优先于标准触控尺寸，卡片内部按钮和文字在极端视口可能显著小于常规可访问性基线；需要对目标最小视口做专项视觉与误触验证。Header 刷新和关闭按钮不参与这项例外。

### Mobile scale floor

**Context**: 任何固定的卡片或按钮最小尺寸都可能在极端矮屏上迫使商品区滚动或破坏 2+3 单屏构图。

**Decision**: 商品卡整体缩放不设置固定像素下限，始终按可用空间继续同比缩小。

**Consequences**: 这是对项目通常 44px 触控目标的明确局部例外；实现和测试优先验证构图完整、无滚动、无溢出，不把卡片内部最小触控尺寸作为硬门槛。

### Zahira dialogue states

**Context**: 扎希拉台词既承担角色表现，也需要解释刷新、购买成功和无可售商品等状态；完全随机会让台词与用户刚执行的动作脱节。

**Decision**: 使用事件分组台词池：打开欢迎语、手动刷新语、购买成功固定感谢语、零候选专用语。购买成功状态以现有感谢立绘和台词覆盖 5 秒，随后恢复最新场景台词；冷却不触发新台词。

**Consequences**: 台词状态需要与批次、购买反馈计时器和空候选状态解耦，并明确事件优先级；刷新可以增加角色感而不干扰购买成功反馈。

### Empty catalog

**Context**: 当用户已经拥有全部一次性商品且没有可继续购买的消耗品时，不应通过伪商品卡或商品区提示破坏草图留白和扎希拉的角色反馈。

**Decision**: 商品区完全留空；扎希拉显示“还在进货中哦，请下次再来吧。”；刷新按钮灰显禁用。

**Consequences**: 空状态的解释完全由可访问的扎希拉台词承担；关闭并重新打开商店后才会重新请求完整商品目录。

### Product card content

**Context**: 移动端 2+3 构图需要控制信息密度，但用户仍需要在购买前看到有限消耗品还能购买多少次。

**Decision**: 卡片保留图片、名称、价格、购买按钮和适用的消耗品库存；不限量显示“不限量”，有限库存显示剩余数量，一次性商品不显示“限购 1”。折扣原价继续保留。

**Consequences**: 库存行随整卡同比缩放；描述、类别、插画署名和持有详情继续由独立商品详情窗口承载。

### Card and detail interaction

**Context**: 卡片需要同时支持快速购买与查看完整说明；取消详情会失去介绍和插画署名入口，而强制先看详情会增加购买步骤。

**Decision**: 沿用当前双路径交互：卡片主体打开独立详情窗口，卡片内购买按钮直接购买并阻止冒泡；键盘 Enter/Space 可从卡片主体打开详情。

**Consequences**: 重构布局时必须保留嵌套交互的事件隔离、焦点样式、详情关闭和购买禁用状态，不能因整卡缩放退化为单一点击目标。

### Desktop balanced seeded placement

**Context**: 用户希望桌面商品陈列每批都像真实摆放一样完全随机，而不仅是固定网格中的随机角度。

**Decision**: 桌面和移动端统一使用五件 2+3、四件 2+2、三件 2+1、一至两件单排居中的数量拓扑。桌面在平衡行槽位内按批次种子轻微扰动位置并为旋转、浮动保留至少 28px 安全间距；移动端保持稳定居中位置并整卡缩放。

**Consequences**: 需要可注入随机源的纯布局算法和确定性拓扑测试；预备下一批时也应生成位置。桌面不会再出现四件 1+3 或三件任意散落，DOM/焦点顺序仍按最终视觉坐标排序，避免无障碍导航跳跃。

### Batch transition

**Context**: 即时替换会产生明显跳变，飞出/落入又会与卡片持续浮动叠加并延长用户等待。

**Decision**: 使用约 `220ms` 的轻量交叉淡入淡出，新卡最多从 `4px` 垂直偏移回到预生成位置；不阻塞窗口关闭。减少动态模式取消位移并压缩为极短淡变或即时替换。

**Consequences**: 过渡只负责说明批次已更换，不承担装饰性编舞；实现应主要使用 opacity/transform 并允许中断和卸载清理。

### Shop title

**Context**: 当前商店弹窗没有语义 header 或可见标题，草图则明确写出“扎希拉商铺”。

**Decision**: 桌面和移动端统一使用“扎希拉商铺”作为可见标题与窗口可访问名称。

**Consequences**: Header 需要新建稳定的语义结构，并保证扎希拉台词即使覆盖部分 header 背景也不能遮挡标题的必要识别和关闭操作。

### Catalog loading and failure

**Context**: 商品区本身承担随机陈列，不希望加载骨架或技术性错误文字破坏构图；扎希拉台词可以用角色化方式解释状态。

**Decision**: 加载时商品区留空并显示扎希拉台词“稍等一下，我正在整理商品哦。”，刷新禁用；失败时显示“进货单好像出了点问题，请再试一次吧。”和现有错误 toast，刷新按钮改为重试。

**Consequences**: 刷新按钮需要区分加载、冷却、可刷新、零候选禁用和错误重试五种状态；重试成功后重新进入初始批次与 3 秒准备冷却。

### Dedicated wallet asset

**Context**: 草图要求“钱包图片 + 金币数量”，而仓库现有 `gacha-coin-bag.svg` 属于抽卡奖励资源，当前商店只使用通用 Lucide 图标。

**Decision**: 为扎希拉商铺新增独立的钱包位图资产，不复用上述资源；钱包图与实时金币数分离渲染。

**Consequences**: 实施阶段使用 image generation 产出 4:3、1024×768 Bright School 手账贴纸风透明项目资源，并在接入前检查边缘、缩放清晰度和桌面/移动构图；通过已确认的共享版本化路径常量支持后续替换。

### Wallet visual direction

**Context**: 钱包需要融入 Bright School 纸张/校园手账语汇，同时只是金币数量的辅助图形，不能抢过商品和扎希拉。

**Decision**: 初版采用扁平 Bright School 手账贴纸风钱包图片，带深色轮廓、纸张贴纸质感和简化高光，无文字、水印或固定数字。

**Consequences**: 资产应以透明背景位图交付；生成图只是默认实现，后续用户可通过确认的集中资源入口替换为自有图片。

### Wallet replacement contract

**Context**: 直接覆盖同名 public 文件可能继续命中旧浏览器缓存，后台 URL 配置又会扩大到接口和持久化改造。

**Decision**: 在共享商店资源模块集中导出钱包图片路径；后续用户可添加新图片并只修改这一处常量，推荐使用版本化文件名。

**Consequences**: 替换不需要调整组件和布局，也不新增后台管理能力；系统设计与资源测试需要记录该单一入口。

### Wallet aspect ratio

**Context**: 钱包贴纸与金币数量并排展示，横向主体比方形图更接近草图中的钱包占位，也能减少无效透明面积。

**Decision**: 使用 4:3、1024×768 透明母版，主体保留安全边距并通过 `object-fit: contain` 缩放。

**Consequences**: 后续替换图片应优先保持 4:3 与透明背景；不同像素尺寸可接受，但组件不得依赖图内文字或固定金币数字。

## Expansion Sweep

- **Future evolution**: 共享钱包资源常量已为替换资源保留单一入口；批次选择逻辑应保持独立，以便未来增加商品数量、刷新策略或冷却规则。
- **Related scenarios**: 后台可能在玩家已打开商店时上架、下架或修改商品；当前商店只在打开时请求完整目录，购买后局部更新单个商品。
- **Failure and edge cases**: 购买和窗口尺寸变化会使预备批次或桌面随机位置失效，必须重算；预加载失败、目录请求失败和零候选已有明确降级路径。

### Catalog synchronization boundary

**Context**: 每轮刷新重新请求目录可以更快看到后台变更，但会让预备批次和无卡顿刷新依赖网络。

**Decision**: 目录只在打开商店和错误重试时请求；手动刷新完全本地化。后台上架/下架在关闭重开后生效。

**Consequences**: 刷新延迟可预测且不受网络波动影响；商店打开期间不承诺目录实时一致性，服务端购买接口仍作为最终可购买性校验。

## Out of Scope (explicit)

- 后台商品管理台的整体视觉重构。
- 商品定价、折扣、金币经济和成就规则的重新平衡。
- 新增支付货币或真实货币购买。
- 更换扎希拉现有两张运行时立绘资源，除非后续需求明确要求。
- 商店打开期间通过轮询、每次刷新请求或服务端推送实时同步后台商品变更。
- 刷新历史、冷却或当前批次的账号级/设备级持久化。
- 钱包图片的后台上传或 URL 配置界面。
