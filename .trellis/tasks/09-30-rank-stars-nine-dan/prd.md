# 段位星数与九段积分制改造

## Goal

替换现有最近十盘升降段与 Elo 混合体系：九段以下用星数，九段用固定胜负积分。已完成运行代码、迁移、展示和相关测试；实际数据库尚未执行启动迁移。

## Requirements (confirmed)

- 用户已确认实施完整方案，星炬、标准、五子棋分别计算并采用新规则，原本不计段位的对局继续不计。
- 前端删除独立积分区域；段位后跟随星数（九段以下）或积分（九段）。四星上限单行展示，六星上限两行各三颗，八星上限两行各四颗；按上限展示槽位并区分已获得与未获得。
- 新账号从三段、2 星开始（用户选择方案 1）。
- 旧账号全部重置为三段、2 星（用户选择迁移方案 2）；具体执行安排在实施迁移时落地。
- 取消旧 Elo 积分系统；九段以下仅使用星数，九段保留本需求定义的独立积分。
- 排行榜先按段位从高到低排序，同段位再按九段积分或九段以下星数从高到低排序。
- 旧积分关联解锁改用段位条件，已经获得的角色与成就保留；用户明确娜波摩应为首次升到六段解锁，不能继续使用旧 1400 分条件。
- 九段以下普通胜局加一星，负局减一星。
- 对局开始前已满星时，本盘为晋级赛：胜则升段，负则减一星。
- 对局开始前为零星时，本盘为降级赛：负则降段，胜则加一星。
- 升段或降段后获得目标段位星数上限的一半；进入九段按积分规则。
- 保留原有 18 级至 1 级；18 级至三段统一四星，四至六段六星，七至八段八星。用户选择保留级位且统一四星的方案。
- 九段不再用星星表示；每次晋入九段均获得 1000 分，包括降至八段后重新晋入（用户选择方案 1）。
- 九段胜局 +200，负局 -250，分数最低为 0。
- 对局开始前九段积分为 0 时进入降级赛：输则降段，赢则 +200。
- 九段降至八段时按目标段位半星规则获得四星。
- 和棋不改变段位、星数或积分；晋级赛、降级赛遇到和棋，下一盘继续（用户已确认）。
- 最低边界为 18 级零星：输棋保持原状态，不降至更低级位、不补半星；赢棋获得一星（用户已确认）。

## Scope Decisions

- 实施范围沿用现有按模式独立战绩：星炬、标准、五子棋均应用新规则并分别重置三段两星；已有不计段位的对局继续不计段位。
- 并列段位与星数/积分采用稳定次序，不再拿旧积分作为排序依据。
- 赛季重置、连胜加星、隐藏实力分均未被用户要求，不自行加入。

## Resolved Migration

- 旧积分成就按原积分对应的段位转换为段位条件，已获得的成就保留。旧 Elo 配置从导出和公开配置中移除，仅保留友谊赛金币奖励设置。

## Implementation Plan

1. 检查数据模型、结算入口、防刷、成就定义、排行榜和后台编辑链路，明确旧字段用途；不擅自把其他积分成就全部改为六段。
2. 实现共享升降段状态转换及边界测试；替换服务器结算和持久化，保持各模式原有计分资格。
3. 迁移前保存可恢复的旧段位/积分及动态解锁资产；一次性重置旧账号，避免服务重启反复重置。
4. 同步排行榜、履历、对局结果、后台和规则文案；移除旧 Elo 配置及遗留积分解锁条件。
5. 更新系统设计文档并生成 HTML，执行相关测试和项目质量检查。

## Acceptance Criteria

- [x] 三个星数档位及晋降段后的目标半星状态正确。
- [x] 打到满星或零星当局不升降段，下一盘按开始前状态判定。
- [x] 八段晋九段与九段零分降八段正确。
- [x] 九段非零积分败局截断到零，不在当局直接降段。
- [x] 旧账号重置为三段两星；旧 Elo 不再参与结算或排行榜。
- [x] 排行榜按段位、对应积分或星数降序，数字级位顺序正确。
- [x] 普通对局、满星晋级赛、零星及九段零分降级赛遇和棋，竞技进度不变，下一盘仍按原状态结算。
- [x] 18 级零星败局保持不变，胜局变为一星。

## Definition of Done

- 需求确认后再实施；覆盖状态转换、结算持久化、重复结算及展示一致性。
- 执行适用的项目质量检查。
- 实施时同步更新系统设计文档，并运行 npm run docs:system-design。
- 旧数据迁移应可追踪并考虑回滚。

## Out of Scope

- 尚未确认的新赛季、连胜奖励、角色独立天梯及匹配算法重做。

## Pre-implementation Findings

- src/shared/rankProgression.js：现有 18 级至 9 段，默认三段，最近十盘七胜晋段、八负降段。
- src/shared/ratingRules.js：Elo、段位差修正、升降段额外积分及防刷配置。
- server/roomRewards.js：按模式更新段位、积分、战绩，并将 spark 镜像到账户字段。
- server/userAssets.js 存在按旧 rating 解锁角色的逻辑；server/achievements.js 存在积分阈值条件；需迁移条件以免将旧阈值误用于九段新积分。
- 本轮核实 server/adminDefaultSnapshot.js 中娜波摩 acquisitionMethod 已为“首次升上6段后自动获得”，但 server/userAssets.js 仍存在 1400 分动态解锁，src/shared/characterFallback.js 也保留旧文案。实施时需检查完整授予链路，统一六段条件并永久保留已获得角色，避免重置后丢失动态解锁资产。
- 前一轮已研究 Chess.com、Riot 与炉石官方机制；本轮按用户选定的星数规则收敛，不采用此前推荐的实力分映射段位方案。
