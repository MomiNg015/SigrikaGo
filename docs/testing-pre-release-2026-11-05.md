## SQLite 对照与修复

Node 只绑定两逻辑 CPU 时，Prisma 6.8.2 仍报告默认池为 33 个 SQLite 连接。独立数据库执行三轮、每轮 100 个并发读写事务，每个房间快照约 65KB：

| 连接数 | 尝试 | 错误 | 最终房间行数 | 耗时 |
| --- | ---: | ---: | ---: | ---: |
| 默认 33 | 300 | 286（P1008/P2028） | 10 | 45.62 秒 |
| 显式 1 | 300 | 0 | 100 | 4.88 秒 |

证据为 `.tmp/pre-release-2026-11-05/sqlite-transaction-probe.json`，脚本为同目录 `sqlite-probe.mjs`。另一轮单纯快照写入对照没有失败，读写事务竞争是关键条件，不能把所有数据库错误一概归因于连接数。

共享 Prisma 客户端通过 `sqliteClientOptions()` 为 `file:` URL 默认追加 `connection_limit=1`，保留路径、其它参数和显式覆盖，不修改环境变量。隔离库回归验证 50 房间、三轮并发事务后每行均保留最新 revision；既有结算事务/幂等回归也通过。

此前 500 在线/100 房的 23 次持久化错误没有具体错误码；本轮证明了可导致超时的连接竞争缺陷，**尚不能认定那 23 次错误全部由此引起**，仍需原负载复测。旧数据保留在[容量记录](./testing-capacity-2026-11-05.md)。

## 复跑入口

`npm run verify:pre-release -- --list` 查看阶段。默认质量→依赖→迁移→备份→浏览器→稳定性→WASM→容量 smoke，串行、失败即停。可选择阶段，但跳过质量时须确认 `dist` 已按当前代码构建。

本机 PowerShell 设置（CPU mask 不能照搬到真正双核主机）：

```powershell
$env:CAPACITY_WINDOWS_LIMITS='1'
$env:CAPACITY_SERVER_AFFINITY='0x05000000'
$env:CAPACITY_SERVER_MEMORY_MIB='3072'
$env:CAPACITY_MIN_FREE_MIB='1024'
$env:CAPACITY_REPORT_DIR='.tmp/pre-release-2026-11-05/resources'
$env:VERIFICATION_REPORT_DIR='.tmp/pre-release-2026-11-05/full'
npm run verify:pre-release
```

3072MiB 是含浏览器/构建的测试树上限。单独容量参考恢复服务上限 1536MiB，并设置独立发压 CPU mask、保持空闲保护。长稳使用真实 move、至少 20 步 `--recycle-after-moves`、HTTP 读取和负载中重启，记录时长/累计结算盘数，不能只延长单盘落子。
