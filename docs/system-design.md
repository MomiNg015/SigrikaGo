## 当前架构摘要

- 前端使用 React 19、Vite 和 Socket.IO client；`src/main.jsx` 只负责浏览器挂载，应用组合根在 `src/app/App.jsx`，业务状态逐步下沉到 `src/app/*` hooks 和独立视图组件，应用级弹窗可见性集中在 `src/app/useOverlayState.js`，房间/回放/结果弹窗会话状态集中在 `src/app/useRoomSessionState.js`，已关闭结果不会因 `room:resume` 再弹，匹配等待/成功过渡状态集中在 `src/app/useMatchSessionState.js`；移动端对弈模式选择弹窗将路数+时间和贴目/规则分成稳定两行，设置弹窗在竖屏下保持标题不被裁切、内部 tab 单行并列且面板区域独立滚动，资料详情对局回放使用固定头部+内部滚动列表，内层 replay table 不再作为滚动容器以免截断触摸滚动链；移动端图标按钮和关闭按钮由最终安全层兜底为 44px 触控目标，主题动效避免宽度布局动画和弹性曲线，邮箱未读数量在菜单按钮上作为绝对定位角标呈现，不参与按钮文字排版；开发期 Vite `/socket.io` 代理会静默处理后端 watch 重启造成的预期 websocket 断连错误。
- 初始前端入口继续避免一次性加载低频生产工具和业务弹窗：`AppRoutes` 通过 `React.lazy`/`Suspense` 延迟加载后台管理台、剧情教学对弈路由和对局资源加载页，`AppOverlays` 延迟加载棋舍、履历、成就、个性化、仓库、排行榜、观战、好友、商店、招募、设置、公告、邮箱和留言板等低频 overlay；后台管理 `src/styles/admin.css` 与剧情教学对弈 `src/styles/room/tutorial-battle-screen.css` 也分别由对应 lazy route 组件直接导入，随路由 CSS chunk 加载，不再进入首屏 `src/styles.css` / 共享 `room.css`；剧情教学目标光圈规则独立在 `src/styles/room/tutorial-battle-screen/target-ring.css`，避免动作按钮与目标标记继续堆进同一个大文件；匹配、结果、toast、约战、真实房间 gameplay 和剧情播放器保持同步入口，避免影响对局与故事关闭/回退路径。客户端新增 `src/app/playableReadyPreload.js` 作为对局前预热层：登录到大厅后在 idle 时预热对局加载页 chunk，桌面端匹配入口 hover/focus 与模式按钮 hover/focus 会主动预热，真正点击匹配时按模式只为技能开启的 `spark` 预热 Pixi；Vite 开发期把 `pixi.js` 与 `pixi.js/unsafe-eval` 排除出 dep optimizer，同时显式 include `pixi.js > @xmldom/xmldom`、`pixi.js > eventemitter3`、`pixi.js > gifuct-js` 和 `pixi.js > ismobilejs` 让 Pixi 源码路径里的 CommonJS/conditional-export 子依赖继续走预打包 ESM 互操作，避免 Pixi 懒加载 WebGLRenderer 等 renderer 模块时命中浏览器缓存里的过期 `.vite/deps` chunk，也避免 raw CJS 子依赖缺少 default/named export 让技能 canvas 卡在 preparing；该层只改善本地缓存和首帧准备，不替代 `room:preload-ready` 服务端屏障。
- 剧情播放器在桌面端和移动端共享 `StoryPlayerModal` 关闭语义：外层遮罩点击、右上关闭入口和快进/跳过入口都先打开同一个跳过/关闭确认层，只有确认按钮才执行实际关闭，避免误触遮罩直接结束剧情。
- Mobile root back handling is centralized in `src/app/modalDismissal.js`: login, preload, home, admin, and battle parent screens show the `确定要退出游戏吗？` confirmation when no functional modal is open; close/cancel buttons and phone back inside functional modals only dismiss the current modal and do not cascade into exit confirmation.
- 后端使用 Express、Socket.IO、Prisma 和 SQLite；`server/index.js` 负责 HTTP/Socket 入口组合，启动数据与 schema 初始化收口在 `server/serverStartup.js`，Socket 连接事件套件由 `server/socketEvents.js` 统一装配，速率保护与匹配、房间连接/恢复、对局/数子/求和/计分、聊天、约战、断线清理等行为继续分布在对应 `server/socket*Events.js` 模块，生产静态托管收口在 `server/staticAssets.js`，认证、商城、抽卡、社交、回放、房间生命周期等已拆为领域模块；匹配或约战创建的房间先进入 `preloading` 阶段，由 `room:preload-ready` 形成双方资源就绪屏障，双方都 ready 后才进入 opening/自动猜先，任一方超过 90 秒未 ready 时服务端发出 `match:preload-timeout` 并中止匹配。
- Server entrypoints run `prisma generate` before `dev:server` and `start` so Prisma Client stays aligned with `prisma/schema.prisma` after schema edits such as StoryScript initial-board columns. On Windows, an already-running Node server can still hold Prisma's query engine DLL open; stop the old server before regenerating or restarting.
- 后台管理新增面向云端运营的分析入口：`概况` 默认呈现“今日简报”，用 `正常 / 需要关注 / 需要处理` 总状态、原因、分级解读和下一步动作替代密集报表；`运营分析` 展示最近日期范围的活跃、注册、对局、玩家分层、经济和模式趋势。后端聚合逻辑集中在 `server/adminAnalytics.js`，通过 `/api/admin/analytics/overview` 与 `/api/admin/analytics/operations` 输出可读摘要，实时在线与匹配/房间统计从 `onlineSessions`、`rooms.js` 运行时边界注入，深度事件暂以 `待接入` 标注。
- 后台管理页是独立的全屏桌面工作台：`.admin-screen` 在后台样式层覆盖基础 1280px 页面宽度限制，使用视口全宽、固定侧栏和可滚动主工作区，避免剧情教学等高密度工具被压窄；最终 `mobile-adaptive/admin-fullscreen.css` 会在主题/HUD 层之后重置 `.app-shell:has(.admin-screen)` 的浅色背景并隐藏游戏化伪背景，确保后台不继承大厅或 HUD 的黑绿外观。
- 角色目录支持后台维护配音人员展示信息：`Character.cvName` 与可选 `cvUrl` 通过 admin/public character payload 下发，棋舍角色详情在桌面把 `CV：{cvName}` 放在角色名右侧，在移动端放在角色名下方；链接只接受 http(s) 或站内路径，并保持继承色、无下划线、无 visited/hover 变色，避免影响标题和 BGM 播放器布局。商城商品同样支持后台维护商品图插画署名：`ShopItem.illustName` 与可选 `illustUrl` 会在商品详情标题区显示 `illust：{illustName}`，移动端堆叠在商品名下方，链接态与纯文本态保持同色、无下划线、无边框、无背景和稳定行高。
- 公告中心是登录玩家功能，不存在访客路径：玩家从大厅右上角操作区打开公告弹窗，弹窗内有“公告 / 更新日志”两类列表，点击条目会在父公告窗口内部挂载与父窗口等大的嵌入式详情层；详情遮罩只覆盖父公告窗口，不覆盖整个视口，也不替换父窗口内容。玩家公告窗口的标题组不使用额外粉色装饰底或虚线线框，标题容器类名避免包含 `lock` 片段以免被 Bright School 锁定态选择器误伤；分段标签、列表行、空/错状态、详情类型标签和详情正文必须沿用其它玩家窗口的 8px 控件圆角、44px 触控目标、Bright School 纸张边框与粉色选中态，并保留足够内边距和行高，避免圆角区域裁切文字。详情头部使用固定垂直节奏，类型标签到标题的距离必须等于标题到时间行的距离；正文面板在详情窗口内占满剩余高度并保留窗口内边距，使短正文也能拉到窗口底部前的安全边界。样式入口 `src/styles/modals/announcement.css` 保持 import-only 并委托到 `src/styles/modals/announcement/` 子文件；Bright School 公告控件修复在 `src/styles/themes/bright-school/surface-contracts/final-announcement-controls.css`，只使用显式公告类名，不再依赖通用子串兜底选择器。最终移动安全层 `src/styles/mobile-adaptive/announcement-detail.css` 会清除通用 `.nested-modal` 的手机全屏定位和 Bright School 全宽覆盖，确保详情层在桌面和移动端都保持父公告窗口内的同尺寸嵌入。后台新增“公告管理”顶级页，统一维护公告与更新日志草稿、发布、取消发布、软删除和预览。后端领域边界在 `server/announcements.js` 与 `server/announcementRoutes.js`，数据由 `AnnouncementEntry` 与 `AnnouncementRead` 持久化，玩家未读只按首次发布时间晚于账号创建时间且尚未打开详情计算。
- 首页公告未读红点在桌面顶栏和移动菜单里都属于公告按钮自身的状态标记；移动端必须像邮箱角标一样以按钮为定位上下文贴到右上角，不能作为菜单行末尾的静态 flex 内容。
- 对局模式由 `src/shared/gameModes.js` 统一配置，前后端共享模式顺序、棋盘大小、贴目、技能开关、时间控制、图标路径和模式选择英文标签；三种模式图标位于 `public/assets/match-modes/`，路径为 `/assets/match-modes/mode-spark.png`、`/assets/match-modes/mode-gomoku.png` 和 `/assets/match-modes/mode-standard.png`。首页铭牌按星炬、标准、五子棋三列显示图标和段位数字，不再显示积分；视觉层只显示 rank 数字，完整“段/级”语义留在 `aria-label`，铭牌专属 CSS 会给三列图标和 WuWa 数字使用更大的显示槽位，避免复用匹配水印尺寸时显得过小。点击匹配入口后的模式选择按钮保留左侧中文标题/规则和右侧人数，同时通过指针透明的居中水印层显示“图标 + WuWa 英文标签”，桌面透明度为 50%，移动端透明度为 20%。
- Bright School 首页的图片式匹配/手册入口和 2x3 工具按钮依赖 WebP 透明图像加 `drop-shadow` 表现纸片厚度；匹配入口 `fantasy-match-entry` 当前 alpha 裁切尺寸为 `2374x1960`，部员手册入口 `book-entry` 为 `705x850`；桌面和移动端都必须保持这些入口、工具 grid 与按钮容器 `overflow: visible`，工具按钮图像自身保留右/下透明 bleed，避免阴影被卡片或最终移动安全层裁切。
- 招募道具运行期图标通过 `src/shared/recruitment.js` 同步给招募、商城和仓库等消费者；后端商品与背包 payload 会把内置招募道具的旧落库 `imageUrl` 归一到当前共享配置，启动回填只匹配每个道具声明的空值或旧默认 SVG 路径。“招新贴报/招新海报”使用 `public/assets/items/recruitment-poster.webp`，由 `C:/codex/image/item/Recruitment_paper.png` 无损转换而来；“先约电台广播券”使用 `public/assets/items/radio-recruitment-ticket.webp`，由 `C:/codex/image/item/boardcast_ticket.png` 转换而来。“彩虹豆豆跳跳糖”的运行期道具图标使用 `public/assets/items/rainbow-bean-candy.webp`，由 `C:/codex/image/item/rainbow-candy-cutout-full.png` 无损转换而来；`server/itemImages.js` 统一让商城商品、仓库道具和玩家侧抽卡奖项/结果归一到当前 WebP，默认快照中的糖果商品和卡池奖励也使用同一路径。`public/assets/promotional/` 仍保留未接入运行时引用的候选宣传图，例如“招新贴报”候选 `recruitment-poster-v1..v3.png` 与“先约电台广播券”候选 `radio-coupon-v1..v3.png`，候选图不进入启动预加载清单，除非后续 UI 明确引用。
- 玩家侧艺术字体作为语义化、白名单式资源使用：`public/assets/fonts/WuWa-Lahai-Roi-Regular.ttf` 通过 `"Sigrika Accent Latin"` 字体族挂到 `--font-display-accent` 与 `--font-numeric-accent`，只覆盖拉丁字母和数字。倒计时数字必须经 `.text-clock-value`，玩家可见积分/rating 数值必须经 `.text-rating-value`，登录页 `SigrikaGo` 英文品牌短标签、首页品牌/模式选择英文水印/锁定占位等氛围短标签可经 `.text-display-accent`；这些艺术字语义类用 `text-transform: uppercase` 让小写拉丁字母视觉显示为大写，但不改源字符串和数据。用户名、后台管理、正文、表单、金币/价格/库存、局数胜负、房间号、时间戳和排行榜名次不使用该字体，后续替换字体只改 token/asset 而不改语义类名。最终 `mobile-adaptive/semantic-accent-typography.css` 在主题层之后回补这三个语义类，避免 Bright School 的广域 `!important` 字体/颜色重置压掉棋钟读秒颜色和 rating 数字字体，并清除 `.text-clock-value` 误继承的徽章背景、边框和阴影；主时间棋钟数字固定为 `#1c171a` 而不是灰色，读秒警告状态保留红色/多色语义，移动端房间玩家条内会把艺术字体棋钟压到更小字号与宽度，避免读秒条被挤出容器。
- Capture-removal counters may be negative and still participate in scoring: Lynae `spray-stone` and QiuYuan `row-slash` subtract 1 removal from the acting player when the skill succeeds, while ChangLi `double-move` adds 1 removal after a completed second placement.
- 当前内置对局模式为 `spark`、`standard` 和 `gomoku`。五子棋沿用 13 路棋盘与星位、5 分钟 30 秒 3 次读秒、自动猜先和独立 `UserModeStats(mode=gomoku)` 段位/积分；需要出战角色但 `skillEnabled=false`，房间 UI 不显示弃手、数子、提子、除子、超频或技能信息。 Gomoku five-in-row results carry `winner.winningLine`; the board keeps a persistent gold highlight on those five stones, live games show the result modal immediately, and replay only shows the highlight.
- 对局结果弹窗是当前玩家视角而不是胜方公告牌：`ResultModal` 通过 `resultPlayerForRoom` 取当前用户的房间玩家作为 `displayPlayer`，胜负/平局/观战只改变 `result-outcome-*` 状态、文案和视觉效果；胜利显示 `赢了耶！` 并保留角色跳动，失败显示 `输掉了...`、灰度冻结当前用户立绘，并叠加 `/assets/effects/result-defeat-rain.gif` 雨云效果。结果奖励中的 rating 数值继续使用 `.text-rating-value`，金币和用户名不使用艺术数字字体；奖励卡片必须有实色语义底，rating 负值用浅红、非负值用浅绿，金币用浅金色，rating 数值内层 span 只继承父奖励卡片底色，不再绘制独立背景、边框或阴影。
- 站点公开配置通过 `SiteSetting` key/value 存储，并由 `src/shared/siteSettings.js` 定义前后端共享默认值；后台系统设置可编辑大厅标题/副标题、关于文本、首页 footer 长文本、加载页提示语集合和全局技能特效开关，`HomeHeader` 从公开配置消费 `homeTitle` 与 `homeSubtitle`，副标题通过 `text-display-accent` 让拉丁/数字走 WuWa 艺术字体且中文回退到 UI 字体，首页在线人数以透明图标+数字 HUD 标签呈现；留言板输入框默认使用更高的写作区域，移动端再按视口高度收敛；footer 支持受限 Markdown 链接，加载页提示语按行维护并在玩家预加载时随机轮播；加载屏内容在桌面、移动端和短视口中保持整屏居中，标题与提示语允许按容器宽度换行，中间加载面板保持透明且不覆盖整页主题背景。
- `ratingRules` controls dynamic rated-match rewards, rank-gap scaling, optional anti-boosting, rank-change rating deltas, and friendly-match coin limits. ## Mailbox System Summary

- Mailbox is an authenticated player/admin HTTP feature. Players open it from the home top-right action area or the mobile menu, read admin-only text mail, manually claim one optional attachment, and can keep at most 20 messages.
- Admins send mailbox batches from the admin console to one user, all current users, or all current plus future users. Item and coin claims update the existing inventory and progress systems.
- Player deletes are soft deletes on `MailboxMessage.deletedAt`; future-eligible global batches still see that delivery history, so a deleted mail is not recreated on the next mailbox summary or list refresh.
- The player mailbox keeps the same list/detail layout for empty inboxes; the left mail list shows the empty state while the detail pane remains reserved. Desktop uses a left-list/right-detail split, while mobile places a horizontally scrollable mail list above the detail pane so newer mail appears on the left and older mail continues to the right. Its player modal title omits the former English subtitle, and the close button stays in the title row on desktop and in the final Bright School portrait mobile safety layer. Mail rows are colored by status: pink for unread/unclaimed, light green for read/unclaimed, and gray for read/completed. The mail detail pane stretches to the bottom of the mailbox content area with modal padding preserved; long mail text scrolls inside the body region while time, title, attachment, and actions stay in the detail frame. The detail pane uses `/assets/mailbox/mail-body-paper.png` as a covered paper background on desktop and mobile, with a light translucent frosted overlay above the art that fades at the edges to protect text readability without hiding the paper, a thicker paper border, and a small lower-right shadow; delete is a small 24px icon-only pink circular trash button in the detail pane's transparent top-right time row.
- App-level overlays must keep `useOverlayState`, `App`, `useAppActions`, and `useOverlayActions` wiring in sync. `closeAllOverlays()` is reused by `match:found`, room resume, and replay entry flows, so a missing overlay setter can break matchmaking before the match-success/preload state is recorded.

## Stability Boundary Update

- 2026-06-27 stability/extensibility hardening keeps production on the current single Node.js room runtime. Multi-instance migration remains a future architecture boundary, but the code now exposes clearer seams: `server/roomQueries.js` can delegate active/watch room lists to an injected read model, `server/serverStartup.js` exports `SERVER_STARTUP_TASK_ORDER`, room-resume stability metrics include the `initial-connect` reason, character-target item ownership uses `publicUserAssets()`, skill effect image URLs live in `src/room/boardSkillEffectAssets.js`, and direct-duel incoming banner state lives in `src/app/useIncomingDuelState.js`.
- Startup preload / room resume race: `useStartupPreload()` now uses `shouldShowStartupPreload({ room: roomRef.current, matchSuccess: matchSuccessRef.current })` before setting `view="preloading"` after `/api/me`; a fast mobile `room:resume` that already restored an active room or pending match cannot be visually covered by the generic login preload route.
- Playable-ready prewarm boundary: `usePlayableReadyPreload()` schedules a home-idle client prewarm after authenticated home entry, while home match controls call `preloadPlayableReady()` on desktop pointer/focus intent and `startMatchTransition()` calls it again for the selected mode. The helper deduplicates module loading, skips Pixi for `standard` and `gomoku`, records lightweight `sigrika:playable-ready-preload` browser metrics, and is explicitly opportunistic: failures never block matchmaking or room recovery.
- 对局刷新/重连稳定性边界：`room:preload-ready` 是服务端 ack 的幂等协议，`BattleAssetPreloadScreen` 在未收到 `{ ok: true }` 前会退避重试并在 socket `connect` 后立即重发；`useRoomMemory` 会同时记住 active room 和 `match-preloading` pending room，`room:resume` 恢复到 `preloading` 玩家房间时重建 `matchSuccess` 并回到 `match-preloading`，从而重新加载本地资源并再次上报 ready。`connectGameSocket()` 先用 `autoConnect: false` 创建 Socket.IO 客户端，安装 `connect`/`room:resume` 等处理器后再主动连接，并在连接后立即 queue 一次幂等 `room:resume`，避免生产同源快速连接或移动端 polling/websocket 时序让刷新恢复只依赖单个 `connect` 回调。前端所有 full room snapshot 在进入 UI 前通过 `normalizeRoomSnapshot()` 补齐 `players`、`spectators`、`chat`、`game.points/history/captures/skillUses` 等安全默认值；`AppErrorBoundary` 包裹应用根，`view="room"` 但缺少 `room` 或 `user` 时显示恢复加载页而不是空白页面。
- Finished-room 恢复边界：`sigrika-last-room-code` 只保存未结束的玩家房间；玩家关闭有效结果或从 finished 房间退出时会持久写入 `sigrika-dismissed-result-room-code` 并清除 last-room。服务端 `room:resume` 对空 roomCode 不再自动拉起 finished room，只有显式 roomCode 才允许恢复历史结果，因此玩家离开结果页后刷新不会在房间回收前再次弹出同一结果。
- 技能演出与音频恢复边界：`BoardSkillEffects` 继续把 Pixi 作为 presentation-only 覆盖层，严格 CSP 环境下先加载 `pixi.js/unsafe-eval` 再加载 `pixi.js`；真实 `.board-effects-canvas` 是技能演出验收条件，不再渲染 DOM/CSS 替代动画。Pixi app 初始化和阻塞型 Pixi sprite 资源加载都会在技能横幅窗口内提前开始，只有两者都完成后才挂载透明 canvas 并进入可见播放，避免贴图未进 Pixi 缓存时由 `Sprite.from()` 读到空纹理或白帧；仅供结算后 DOM marker 使用的资源（如 Voyage Star crater WebP）仍属于非阻塞预热资源，不能延迟程序化 Pixi cast。协议接管和陨石擦除等临时 Pixi 残留层需要在演出结束前淡出，收尾清理必须先把 `.board-effects-canvas` 从 overlay host 摘除，再销毁 Pixi/WebGL app，避免 WebGL context teardown 在仍参与合成时露出底帧。Pixi 初始化、WebGL、贴图、renderer 或 ticker 异常只会标记 `data-effect-failed` / `data-effect-error`、清理 sound timers 和 canvas，并保持对局页面不白屏，准生产测试仍判该技能失败。本地 Vite dev server 不预优化 Pixi 入口，但会预优化 Pixi 的嵌套 CommonJS/conditional-export 子依赖以保留 ESM 互操作，避免开发期浏览器继续请求已经失效的 optimized renderer 文件，或直接加载 raw CJS 子依赖导致技能 canvas 没有挂载。BGM 加载会校验 HTTP `response.ok`、记录 decode/fetch 失败源，WebAudio 调度失败时使用 `Audio` fallback，并在 `room:update` 音频基线、socket 重连、`pageshow`、可见性恢复和首次交互后恢复当前曲目；组件级 `BackgroundMusic` 卸载时会立即停止 WebAudio/HTML fallback、清空当前曲目并废弃未完成调度，避免局部界面退出后残留 BGM。
- 生产缓存边界：`server/staticAssets.js` 只对 Vite hash 产物设置一年 immutable；`public/assets/**` 下的运行时图片、WebP、SVG、音频和技能资源保留短缓存/ETag，云端同名替换资源时不会被旧 immutable 缓存长期锁住。
- 本地准生产稳定性验证入口是 `npm run verify:stability`：脚本先执行 Vite production build，再通过 `playwright.stability.config.js` 启动 `scripts/start-stability-server.mjs`，以 `LOCAL_PROD_STATIC=1` 让同一个 Express/Socket.IO 服务托管 `dist/` 并保留非 production 的本地测试能力；默认端口是 `4173`，可用 `STABILITY_PORT` 或 `PORT` 覆盖。稳定性服务器使用 `NODE_ENV=stability`，仅在该环境把 `/api/auth` 限流上限提高到足够覆盖桌面和移动两组注册/刷新流量，生产环境仍保持严格 auth 限流。稳定性用例覆盖生产包缓存边界、运行时资源失败不白屏、桌面/移动浏览器的对局刷新恢复、星炬与爱弥斯 `hidden-hand` / `voyage-star` 真实 Pixi canvas、finished 房间退出后刷新不重弹结果、以及对手重连不触发本机“操作频繁”toast；它减少云服务器反复部署验证，但最终上线仍需确认 Nginx/CDN 没有覆盖 Node 返回的缓存头。
- GitHub Actions 的 `CI` workflow 是远端质量门：pull request 和 `master` push 会执行 `npm ci`、`npm test`、`npm run build`、示例生产配置检查和 `npm run docs:system-design`，与本地交付门保持一致。
- App-level overlays are registered in `src/app/overlayRegistry.js`. `useOverlayState`, `modalDismissal`, `useOverlayActions`, and `App.jsx` derive overlay state, close-all behavior, and topmost-modal dismissal from that registry so new overlays do not need separate manual wiring that can break matchmaking or room recovery.
- Mailbox summary polling lives in `src/app/useMailboxSummary.js`, and recruitment ready-state polling/timing lives in `src/app/useRecruitmentReadyState.js`, keeping the app composition root focused on wiring rather than feature-specific polling loops.
- Room broadcast persistence policy is declared in `server/roomBroadcasts.js`: full updates and default patches force persistence, while clock and presence-style patch categories remain throttled/lightweight.
- Finished valid rooms do not close until `server/roomResultPersistence.js` has saved the result record; `server/roomCloseLifecycle.js` retries failed result saves before emitting `room:closed` or deleting persisted room state.
- Gameplay actions pass through the phase matrix in `server/roomActionPhaseGuards.js` before reaching move/pass/resign/skill resolution, so opening, skill preview, dead-stone marking, result review, and finished phases cannot be overwritten by generic board actions.
- Client patch-gap recovery is debounced in `src/app/socketHandlers.js`: duplicate gapped `room:patch` payloads for the same room/revision emit at most one `room:resume` per debounce window, room-code-level in-flight/cooldown state suppresses resume storms during presence reconnects, and full `room:update` / `room:resume` snapshots clear that debounce state. `server/socketGuards.js` separates recovery events (`room:resume`, `room:preload-ready`) from user actions, so excessive recovery traffic can be acked/rejected without showing the player-facing “操作频繁” toast that still protects `game:action` and chat.
- Legacy-to-structured asset sync only deletes structured rows whose `source` is `legacy`; feature-owned rows from achievements, gacha, mailbox, recruitment, or future flows stay owned by their source-specific paths and are merged for public projection.

## Story Script Summary

- Story tutorial scripts keep one script-level default `initialBoard`, but nodes may now use `type: "board-setup"` with a node-local `boardSetup` snapshot to enter or switch a full-screen local teaching battle inside a branch. This remains plain `nodes` JSON and does not add a table, DSL, or new graph model. `TutorialSessionModal` delegates board setup nodes to `TutorialBattleScreen`, which reuses `RoomBattleStage` with a local room snapshot; the admin current-step preview finds a reachable path from `startNodeId` through both `nextNodeId` and option targets before silently replaying board setup, moves, skills, and resign actions so branch previews inherit the correct board state.
- Teaching battle scripts also support in-battle dialogue flow nodes without changing the StoryScript storage model. `npc-dialogue` shows an NPC bubble in the full battle screen without making a move, while `player-choice` shows centered reply options and records the reply into the read-only battle chat log. NPC move/skill/dialogue nodes may carry `actionStartDelaySeconds`, `replyDelaySeconds`, `manualContinueEnabled`, `autoContinueEnabled`, `autoContinueDelaySeconds`, `actor`, `skillCharacterId`, and optional reply options. Battle node progression is authored as one advance mode: new admin nodes default to automatic progression and write `manualContinueEnabled: false` plus `autoContinueEnabled: true`, while manual mode writes the inverse and shows the post-node "继续" button without starting an automatic timer. The old boolean fields remain in the JSON so existing scripts round-trip through the API; runtime helpers collapse them to a single active mode. In automatic mode, blank `autoContinueDelaySeconds` means 1.5 seconds after `npc-dialogue` typewriter completion and 0 seconds for other battle nodes. The completed node then enters `nextNodeId` or reveals that node's reply options. Story and battle options may carry `transitionDelaySeconds`, shown in admin as "选择后等待", which waits after the user clicks an option before entering its target or closing the script; blank values mean 0 seconds. During progression waits the current surface stays mounted, choices hide after click, and duplicate controls are disabled. The action panel never renders free-text hints: it shows only concrete teaching buttons such as "继续", skill, counting, or resign, otherwise it remains empty while board highlights, reply options, NPC bubbles, chat, and toast feedback carry the instructional text. Admin preview may still expose a preview-only "立即继续" button for timer waits. `TutorialBattleScreen` keys node initialization by current node id so clearing a progression wait does not re-run the same node setup or hide newly revealed reply options. NPC actions run automatically after the configured delay, player move/skill/button nodes hard-highlight the scripted target/action, and wrong player actions show teaching toasts instead of sending room actions. `TutorialBattleScreen` now selects `DesktopRoomLayout` or `MobileRoomLayout` from the same responsive hook as real rooms, hides room utility controls and member panels, keeps only the exit/skip affordance, compacts chat messages by removing hand/time/role suffixes, and restores real room move sounds plus battle/skill BGM through `useRoomAudioEffects` and `BackgroundMusic`. Reply options appear over a full-screen dark scrim as button-only controls without a visible choice card, while the active NPC bubble remains visible above the scrim, uses the NPC character palette as a restrained accent, and types body text progressively while showing the speaker name immediately; under Bright School, reply option hover/focus reuses the home utility-card lift, hard shadow and slight tilt via `src/styles/themes/bright-school/room/tutorial-choice-interactions.css` without changing teaching action buttons. Teaching action buttons stretch across the board action area with a light-green target affordance, mobile teaching action bars keep button-only controls filling the action dock width with only normal padding, mobile teaching button labels are centered inside the stretched button, timer panels reuse the normal `TimeBar` layout without tutorial-specific centering overrides, and no-character player panels preserve empty portrait/role/skill placeholders on desktop and mobile; desktop battle tutorials size the empty portrait frame to the same outer height as real character portrait frames, and both desktop and mobile empty portrait frames follow the player's black/white side background. A `story` node reached inside `TutorialBattleScreen` exits the battle view through the full-screen 3-second "正在收拾棋盘..." loading screen, disables the local teaching battle BGM before the transition, pauses global BGM during the transition, and resumes ordinary story playback from that node without letting the old battle BGM restart; entering or switching `board-setup` uses the shared `AssetPreloadScreen` template for the full-screen 3-second "正在激烈对局中..." loading screen. Story-to-battle, battle-to-story, and board-setup handoffs arm the loading state before the next frame is painted, so users do not see a one-frame battle shell, setup placeholder, or home screen flash between story surfaces.

- 剧情脚本现在也是本地对弈教学脚本：`StoryScript` 草稿/发布数据包含可选 `initialBoard`，节点 `type` 支持 `story`、`board-setup`、玩家/NPC 落子、玩家/NPC 技能、数目相关节点和 `resign`。纯剧情段仍由 `TutorialSessionModal`/`StoryPlayerModal` 播放；运行到 `board-setup` 后切到独立 `tutorial-battle` view 或后台全屏预览层，`TutorialBattleScreen` 复用完整 `RoomBattleStage`、双方信息框、棋盘和操作栏，但使用本地 room 快照，不创建 socket 房间、不影响匹配/天梯/录像。`board-setup` 节点额外保存玩家执棋、玩家角色（可为空）、NPC 角色、NPC 名称和入场提示；玩家无角色时不显示立绘和技能，玩家侧不显示段位，且空立绘槽和技能占位在桌面和移动房间布局中保持与有角色时相同的占位尺寸，避免双方信息区不对称。玩家落子/技能目标硬门禁，NPC 落子、技能和认输按脚本推进，技能教学包含点击技能、选点/确认、`SkillBanner`/pendingSkill 演出和结果落地；回复/教学操作按钮默认浅绿色，按下才转粉色；目标点金色光圈由棋盘点按钮内的真实 `.tutorial-target-ring` 子元素绘制，桌面端使用更大的双层描边和外发光，移动端保留尺寸上限，并在 Bright School `button > *` 重置后保持交叉点居中。进入 `tutorial-battle` 的 Suspense fallback、`TutorialSessionModal` 的 story-to-battle 首帧和 `TutorialBattleScreen` 内部 board-setup 切换都使用同一套全屏 `AssetPreloadScreen`，避免普通加载页或 setup 占位闪现。后台剧情脚本页可编辑初始棋盘、节点类型、提示、颜色、坐标、技能 ID 和局面角色配置，初始棋子既可用坐标文本维护，也可通过“可视化摆棋”弹窗点选黑棋/白棋/擦除并保存回写；右侧预览只提供全屏预览入口，避免把完整对弈界面压进窄栏。发布时会拒绝无法解析的技能 ID，避免运行时才出现缺失技能。
