## 接下来的主要工作

用户已明确下一阶段方向：**用多表情的标准立绘逐步替代现有 Q 版立绘，逐步重新调整各个含有角色立绘的区域，使之美观、契合。** 每次推进一个场景，完成可见效果和验证后再进入下一处；本次整理提交不直接开始这些界面改造。

### 建议推进顺序

1. **建立角色与场景清单。** 从现有标准立绘资源、manifest 和分阶段方案确认角色 ID、可用表情及所有立绘入口。西格莉卡、达妮娅、爱弥斯已有标准资源，先用这些真实素材推进；其他角色待有对应素材后接入，不伪造资源或错误映射。
2. **部员手册与角色详情。** 以已有独立样板为参考，调整列表胸像、详情大立绘、完整查看和出战控件，让新人物比例与纸面卡片、文字、按钮和滚动区形成完整布局。
3. **首页学生证、履历与详细资料。** 分别选择适合小头像和大展示的构图，重排身份信息和战绩区域，保证人物轮廓、名称及操作清晰，长内容独立滚动。
4. **选人、招募、装扮及其他角色展示。** 逐一检查实际入口与角色形态优先级，调整卡片/窗口的留白、比例和裁切，保留当前选择、拥有、装备和特殊造型语义。
5. **对局展示与演出。** 依次处理玩家信息、猜先、队际头像、技能展示及结算等区域。常驻区保持信息可读，演出区结合权威事件选用表情；调整人物和 UI 的层次，同时保留棋盘操作、棋钟、技能反馈和既有游戏规则。
6. **全场景回看。** 排查剩余 Q 版入口、加载失败和旧数据回退，核对桌面与手机竖屏的一致性，并同步资源入口、预加载、设计文档和相关测试。

### 每个场景的设计与验收

- 替换图片时同步调整容器、裁切、对齐、留白、背景层次及文字/按钮位置。根据用途选择全身、膝上、胸像或头像，不将同一张全身图直接塞入所有旧 Q 版尺寸。
- 尊重素材透明轮廓和画幅，保持等比、不拉伸；头饰和脸部应完整，人物突出纸面时预留空间，不压住正文、操作或棋盘。
- 沿用当前 Bright School 手绘纸面视觉及现有主题体系，让人物和窗口契合；不自行增加无关提示、统计、装饰和游戏功能。
- 剧情表情继续使用作者配置；对局表情通过真实状态/事件驱动，明确默认、覆盖、恢复与旧资源回退，不随机猜测台词或改变规则。
- 桌面及手机竖屏验证真实素材、表情切换、长文、特殊造型、空状态、失败回退和交互，重点检查 390px 与 360px 宽度的裁切、遮挡、横向溢出和滚动。后台只验证桌面。
- 先检查实际可见结果，再完成针对性回归；涉及资源、样式或运行行为时同步系统设计，维护对应合同。各场景完成范围和未完成项更新在本说明及相关任务中。

## 原电脑离开前

1. 用 `git status --short --branch` 确认分支和改动范围；保留需要继续的源码、资源、文档、迁移文件、测试及 Trellis 任务记录。
2. 将选定内容提交并推送。交接分支的推送命令为 `git push -u origin master`；如果后续工作另开分支，接续时两台电脑切到同一分支。
3. 停止写入本地数据库的开发服务和后台任务，再复制数据库与上传资源，保留原电脑的数据库副本。确认实际 `DATABASE_URL` 和 `UPLOAD_DIR` 是否指向项目外。
4. 如有只存在浏览器中的未保存剧情/Excel 草稿，先保存或导出；浏览器草稿和登录状态不会随 Git 代码迁移。

需要分别处理的内容：

| 内容 | 获取方式 |
| --- | --- |
| 已提交源码、资源、文档、迁移与测试 | 随对应分支 clone / pull |
| `AGENTS.md`、`.trellis/`、`.agents/`、项目 `.codex/` | 已有文件由 Git 跟踪；新增任务及规范仍要实际纳入提交 |
| `.env` | Git 忽略，私下复制到新电脑；文档与提交中不写入其内容 |
| SQLite 开发库 | Git 忽略；当前项目有 `prisma/dev.db`，以实际 `DATABASE_URL` 为准，单独备份复制 |
| 上传目录 | 默认 `public/uploads/`；该目录没有整体忽略，但仅纳入提交的文件会随 Git 获取，剩余资源另行复制 |
| `.trellis/.developer`、`.current-task`、`.runtime/` | 属于本机忽略状态；新电脑重新初始化身份并选择需要继续的任务 |
| `node_modules/`、`dist/`、`.tmp/` 等 | 依赖和产物在新电脑重新生成，测试原始日志与截图如需保留则另行备份 |

个人目录中的技能、记忆和美术源文件也不属于项目 Git。需要继续使用时，单独迁移原电脑的 `C:\Users\Moming\.codex\skills`、`C:\Users\Moming\.agents\skills`、`C:\Users\Moming\.codex\memories` 及所需的 `C:\Users\Moming\.codex\visualizations` 素材。新电脑用户名不同时放到对应用户目录，并检查配置里的旧绝对路径；插件及外部服务连接按新电脑环境重新配置。

## 新电脑获取和启动

安装 Git、Codex、Node.js 和 Python 3；Node.js 建议先使用与原电脑一致的 `24.15.0`。项目未声明最低 Node 版本，不能将本机版本当作已经验证过的全部兼容范围。建议仍使用 `C:\codex\SigrikaGo`，减少旧记录中的路径差异。

第一次获取项目，原电脑必须先把目标分支推送成功：

```powershell
git clone --branch master https://github.com/MomiNg015/SigrikaGo.git C:\codex\SigrikaGo
cd C:\codex\SigrikaGo
```

如果新电脑已有该仓库，先确认没有需要保留的本地改动，再获取同一分支：

```powershell
cd C:\codex\SigrikaGo
git status --short --branch
git fetch origin
git switch master
git pull --ff-only origin master
```

如有本地改动或分支分歧，先核对并保留，不用 `reset --hard`、`clean` 或覆盖目录来强行同步。

将原电脑的 `.env`、数据库和缺失上传资源放回正确位置。没有旧数据时，依据 [README](../README.md) 和 [部署手册](./deployment.md) 配置新开发环境，不能把新空库误作原电脑数据库的完整副本。

然后安装依赖并启动：

```powershell
npm ci
npm run dev
```

依赖安装和开发服务入口会生成 Prisma Client。复制现有可运行开发库，不因换电脑而无条件执行 `prisma db push`、`prisma migrate resolve` 或重建数据库。若另有版本迁移需求，先备份，核查迁移历史，再按部署手册处理；当前没有名为 `prisma:migrate:deploy` 的 npm 脚本，正式 Prisma 命令是 `npx prisma migrate deploy`，也不能直接用于未经基线核验的所有旧库。

服务启动会运行已有 schema guard 和数据初始化；尚未完成星数迁移的旧库可能在首次启动时迁到三段 2 星，已完成的库通过数据库内回执跳过重跑。因此应在首次启动前保留数据库副本，不能仅以“服务能打开”判断旧数据完全一致。

Trellis 的本地开发者身份若不存在，初始化后读取上下文：

```powershell
py -3 ./.trellis/scripts/init_developer.py Moming
py -3 ./.trellis/scripts/get_context.py
```

仓库里有多项历史 `in_progress` 任务；它们不等于全部都需要立即恢复。由用户指定接续范围，再阅读对应 PRD、最新追加需求和验证记录，不批量启动或归档旧任务。

标准剧情节点的 `long-text-compress-portrait` 效果按当前可见正文、角色名和操作区的实际高度，将底部固定的对话框向上扩展，上限为舞台高度减 90px；超出正文继续内部滚动。桌面立绘保持位置，760px 以下立绘按对话框增加的高度同步上移，舞台 `overflow: clip` 禁止立绘越过窗口可见边界，允许头部被裁切。普通节点继续固定裁切。尺寸变化跟随逐字效果，减少动态偏好关闭过渡而保留最终布局。选项滚动区保留上/右/下/左 5/8/9/5px 阴影与焦点留白，采用暖纸底色加角色主题色，统一悬停和按下状态。
