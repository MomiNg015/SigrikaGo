## Realtime Performance Notes

- Room clock ticks no longer use the full `room:update` payload during normal play. `server/rooms.js` emits a lightweight `room:clock` event once per second with `roomCode`, `activeColor`, `serverNow`, and each player's current `time`.
- Player chat and room presence now use general room patch paths: `server/socketChatEvents.js` broadcasts `room:patch` with `type: "chat:append"`, while `server/socketRoomEvents.js` and `server/socketDisconnectEvents.js` use `broadcastRoomPresencePatch()` for disconnect, reconnect, spectator membership, and leave changes. `server/roomBroadcasts.js` increments room `revision`, emits `eventId`, `baseRevision`, and `revision`; full room updates and default patches still force persistence, but chat and presence patches explicitly opt into throttled persistence because connection lifecycle mutations already force-save the authoritative room before the lightweight presence broadcast. `src/app/roomPatch.js` applies `chat:append` idempotently and applies `presence:update` by replacing player/spectator/chat slices while preserving `game` and structurally sharing unchanged entries. `src/app/socketHandlers.js` filters missing-room, wrong-room, unknown, stale, and malformed patches before scheduling React state work; if the client sees a patch gap, it rejects the patch and emits `room:resume` to recover the authoritative snapshot. Duplicate gapped patch payloads for the same room/revision are debounced so a bad network burst cannot spam resume requests, and authoritative `room:update` / `room:resume` snapshots clear the debounce state. Full `room:update` remains the authoritative path for the joining/resuming socket, match found, moves, skills, phase changes, scoring, draw/counting flows, timeout transitions, and patch recovery.
- Full `room:update` remains the authoritative synchronization path for match found, the socket that just joined/resumed, moves, skills, phase changes, scoring, draw/counting flows, timeout transitions, and any patch-gap recovery.
- `server/roomBroadcasts.js` is the single backend emit boundary for room snapshot updates, lightweight clock updates, lightweight patch updates, room toasts, and close events. It skips disconnected participants, owns patch revision metadata, defaults patch persistence to forced writes, allows chat/presence callers to opt into throttled persistence, and builds `presence:update` from the existing room view projection so player/spectator payload shape stays aligned with full snapshots.
- `server/roomRuntime.js` is the backend room runtime adapter boundary. It wires `server/roomStatePersistence.js` into `server/roomBroadcasts.js`, centralizing forced/throttled persistence callbacks, per-room serialized snapshot writes, room-specific flush consistency points, full-room broadcast persistence injection, and room toast forwarding outside the lifecycle composition module.
- `server/roomPresence.js` is the backend participant-state boundary for players plus spectators. Room broadcasting, watch-room summaries, finished-room close extension, and empty-active-room closure all use it for connected-participant and all-players-disconnected decisions.
- `server/roomMatchmakingQueue.js` is the backend matchmaking queue boundary for waiting-player state. Matchmaking joins, leaves, disconnect cleanup, per-mode counts, and custom `canPair` filters go through this module, while room creation and match-success delivery stay in `server/rooms.js`.
- `server/roomFactory.js` is the backend room creation boundary. Initial room shape, random room code generation, player color assignment, mode-specific room-user projection, opening phase, and initial clock fields live there.
- `server/roomSkillMessages.js` is the backend skill-message formatting boundary. Skill use notices, custom `systemMessage` template replacement, point labels, and stone labels live there so room lifecycle code does not own display-string rules.
- `server/roomTimers.js` is the backend timer bookkeeping boundary for room intervals and tracked timeouts. Room lifecycle code should schedule through this module so timeout ids are removed after firing and cleared consistently during room shutdown or empty-room cancellation.
- `server/roomSystemMessages.js` is the backend room chat-log mutation boundary for system messages. Generic system notices, notice-list appends, and restored disconnect notices live there so room lifecycle code can decide when notices occur without owning message object shape or reconnect-recovery text deduplication.
- `server/roomActionValidation.js` is the backend room action point-validation boundary. Room action handlers delegate point-target validation there, while the module forwards board coordinate errors from `server/security.js` unchanged.
- `server/roomCloseLifecycle.js` is the backend room close lifecycle boundary. Finished-room close scheduling, invalid-room short close delay, connected-participant close extension, `room:closed` payload construction, persisted-room deletion trigger, empty-active-room invalidation, and empty-room close cancellation live there behind injected persistence/timer/broadcast dependencies; the `rooms.js` composition waits for pending snapshot upserts for the same room before deleting persisted close-cleanup state.
- `server/roomDeadlineScheduler.js` is the backend room deadline scheduling boundary. Opening delay, initial passive skill delay, counting-request timeout, draw-request timeout, result-review timeout, and restored pending-deadline scheduling live there behind injected room lookup, timer, broadcast, and lifecycle callbacks.
- `server/roomResultPersistence.js` is the backend room result persistence boundary. Finished-room record creation, invalid-result record skipping, draw mode-stat increments, decisive reward application, user stat writes, progress ledger entries, and item-effect cleanup operations live there so room lifecycle code only triggers result saving.
- `server/roomSkillResolution.js` is the backend skill-preview lifecycle boundary. Active/passive skill preview setup, persisted `pendingSkillResolution` snapshots, restored preview delay scheduling, preview payload metadata, and resolution completion side effects live there so new skill effects do not add more timing and preview-state branching to `server/rooms.js`.
- `server/roomClockLifecycle.js` is the backend per-room clock tick boundary. Playing-phase tick handling, disconnected-player empty-room scheduling, timeout finish handling, and the choice between lightweight `room:clock` and full room broadcasts live there so future clock-throttling or patch-broadcast work has one server-side entry point.
- `server/roomRestoreLifecycle.js` is the backend restored-room timer resume boundary. Finished-room close windows, opening deadlines, restored pending skill previews, active room deadlines, and empty-room close scheduling are selected there so process-restart recovery has one auditable scheduling entry point.
- `server/roomPersistenceRestoreLifecycle.js` is the backend persisted-room restore orchestration boundary. Loading persisted rows, parsing/hydrating snapshots, adding restored disconnect notices, registering rooms, invoking restore-time timer decisions, force-persisting resumable rooms, and continuing past bad rows now live outside `server/rooms.js`.
- `server/roomOpeningLifecycle.js` is the backend opening transition boundary. Opening completion now centralizes the transition to `playing`, game-start notice, `lastTick` refresh, full room broadcast, and initial passive-skill scheduling handoff.
- `server/roomConnectionLifecycle.js` is the backend room connection-state boundary. Player reconnects, spectator joins/leaves, socket disconnect cleanup, empty-room close handoff, and forced room persistence after connection changes live there; it receives socket lookup/register/unregister callbacks from `server/roomMembershipIndex.js`, so `detachSocket()` handles only rooms currently indexed for that socket instead of scanning every room.
- `server/roomRequestLifecycle.js` is the backend counting/draw/scoring request entry boundary. Room-code validation, room/player lookup, phase precondition checks, scoring point validation, and delegation into `server/roomScoringFlow.js` live there so future request types can share one validation and dispatch shape.
- `server/roomCreationLifecycle.js` is the backend room creation orchestration boundary. Matched matchmaking joins and direct duel acceptance share creation notices, room registration, one initial forced persistence, clock/preload scheduling, and one viewer-specific `match:found` delivery per player. It no longer follows `match:found` with a duplicate full-room broadcast.
- `server/roomActionLifecycle.js` is the backend gameplay action entry boundary. Game actions now share room-code validation, room lookup, point validation, player lookup, pending-skill rejection, test-action dispatch, skill-action dispatch, and standard action delegation in one focused module.
- `server/roomActionPhaseGuards.js` is the backend gameplay phase matrix. It keeps standard board actions and active skills from mutating opening, preview, scoring, review, or finished rooms before action-specific reducers run, while explicitly documenting the limited non-playing phases where resign remains accepted.
- `server/roomChatLifecycle.js` is the backend room chat entry boundary. Chat sends now share room-code validation, text normalization, room lookup, message id creation, current move-number capture, chat payload shape, and `{ room, message }` mutation result in one focused module so socket code can emit append-only chat patches without rebuilding a viewer-specific room snapshot.
- `server/roomQueries.js` is the backend room read-model boundary. Active-room lists and watch-room summaries can delegate to an injected `roomReadModel`; the current single-process fallback still scans current rooms for projection. Active membership checks and user room lookup delegate to `server/roomMembershipIndex.js` when available. The index is populated by room creation and persisted-room restore, maintained during room connection/leave/disconnect, cleared by room close and tests, and prefers unfinished active rooms over finished review rooms for the same user so reconnect/resume lands on the playable match first; participant counts and player summaries continue to come from `server/roomPresence.js`.
- `server/roomView.js` builds only the needed board projection for player viewers. Spectators use `game` as the canonical black projection and receive only the white difference projection as `gameViews.white`; the frontend keeps black/white switching compatible without serializing the black view twice.
- `server/serverLifecycle.js` guards local development startup and production shutdown: occupied port 3001 gets an explicit `EADDRINUSE` message, while SIGINT/SIGTERM and managed child shutdown use the drain/Socket.IO/HTTP/persistence/Prisma sequence.
- The frontend applies full `room:update` snapshots, live `room:resume` snapshots, and pending match-success room snapshots through `src/app/roomSnapshot.js`. Same-room snapshots are structurally shared before entering React state, so duplicate updates, reconnect resumes, or match-success follow-up updates can return the current room object and unchanged `game.points`, player entries, chat messages, and nested view data keep their existing references. Duplicate pending match-success snapshots are consumed without scheduling a fresh `{ startedAt, room }` wrapper. Room views also carry the latest patch `revision` so clients can validate future patch continuity.
- The frontend merges `room:clock` through `src/app/roomClock.js`, updating only changed player timer objects while preserving the existing `room.game` object reference. `src/app/socketHandlers.js` skips stale clock payloads before scheduling React state work, routes pending-match clocks only to the match transition state, skips unchanged pending-match clock payloads before scheduling `setMatchSuccess`, keeps duplicate `lobby:stats` and `match:waiting` payloads from replacing unchanged app-shell state objects, suppresses repeated `duel:incoming` request ids before scheduling banner/audio work, and normalizes incomplete full snapshots through `src/app/roomSnapshot.js` before structural sharing so missing `players`, `spectators`, `chat`, `points`, `history`, `captures`, or `skillUses` cannot crash UI recovery paths.
- `src/room/Board.jsx` is memoized with a board-specific prop comparison so timer-only updates can refresh player clocks without re-rendering the board. Handler identity changes intentionally re-render only the board shell to refresh `handlersRef.current`; `src/room/actions/useRoomPointActions.js` keeps point handlers `useCallback`-stable across player timer object churn, and `src/room/RoomBattleStage.jsx` passes stable board, action-bar, and floating-layer callbacks instead of inline room-widget props; individual point buttons keep a stable handler ref and remain memoized so local confirmation, marker, decoration, scoring, and click-handler updates do not force all 13-line or 19-line intersections to re-render. `src/room/ChatBox.jsx`, `src/room/RoomPeopleList.jsx`, `src/room/OperationHint.jsx`, and `src/room/ActionBar.jsx` are memoized with chat/member/action-hint/action-control comparators that ignore player time updates from `room:clock` while still rerendering for chat content, chat-name metadata, connection state, membership, user display metadata, phase/turn, winner, skill uses, decision locks, replay step, and request/scoring changes. `src/room/RoomScreen.jsx` also keeps pass/resign/exit confirmation handlers and coordinate/move toggles stable, while `RoomHeader` owns the finished-room close countdown timer locally so those ticks do not re-run the full room screen or recreate action-control props. Timed draw/counting/result request toasts use `timedRoomRequestEffectKey()` so player-time-only `room:clock` updates do not rerun request-toast effects.
- `src/room/PlayerInfo.jsx` is memoized with a player/game-slice comparison so room clock ticks only re-render the player panel whose timer or relevant game slice changed, which is especially important when item effects swap portraits to animated assets.
- Home and Bright School utility hover performance keeps the existing visible motion contract and promotes only the transform surfaces that already animate. `.home-image-entry`, Bright School `.utility-entry`, and `.utility-entry-art` keep their current transform/filter timing and reduced-motion behavior, while `will-change: transform` lets cloud-hosted builds avoid avoidable repaint jank without changing the effect.
- `src/app/roomUserSync.js` merges the current user from room payloads by comparing only fields present in the room user payload, rather than stringifying the whole current user. This keeps item/effect synchronization cheap as the local user state gains more client-only fields.
- `src/shared/gameBoard.js` resolves standard board point ids by direct row-major index before falling back to id search. This keeps capture, liberty, territory, skill, and replay logic from repeatedly scanning the full point array on normal 13x13 states; `src/shared/game.js` re-exports the helper for existing callers.
- `collectGroup` uses a cursor-based breadth-first queue instead of `Array.shift()`, avoiding repeated array reindexing during liberty/capture checks.
- Dead-stone expansion and territory flood-fill use the same cursor-based queue pattern, reducing extra array churn during scoring and result review.

## App Stability Debt Reduction

- App-level overlay debt is reduced by `src/app/overlayRegistry.js`. Overlay state keys, React prop names, setter names, close-all behavior, and modal dismissal ordering now share one registry. This protects `match:found`, room resume, replay entry, desktop Escape, and mobile/browser back handling from future overlay additions that forget one wiring path.
- App-shell composition debt is further reduced by `src/app/appShellProps.js`: `App.jsx` now derives registry-backed overlay props once, then builds route and overlay adapter objects for `AppRoutes` and `AppOverlays`. Future player-facing features should extend the registry or focused adapter contract plus tests instead of adding another long flat prop list to the composition root.
- `src/app/useMailboxSummary.js` and `src/app/useRecruitmentReadyState.js` move feature-specific polling and readyAt timing out of `src/app/App.jsx`, leaving the app composition root to connect feature hooks to routes/overlays. Future app-shell features should follow this pattern instead of adding more inline polling loops to `App.jsx`.
- `src/app/useIncomingDuelState.js` moves direct-duel incoming request state out of `App.jsx`, matching the app-shell hook pattern used for overlays, room sessions, match transitions, mailbox summary, recruitment timing, and audio runtime.
- App-level render failures are contained by `src/app/AppErrorBoundary.jsx`, and `AppRoutes` renders the normal preload recovery shell when `view="room"` lacks `room` or `user`. This keeps reconnect/startup races and unexpected child render errors from producing a blank page.
- `server/userAssets.js` now treats legacy string-field mirroring as source-scoped synchronization. Only rows with `source = "legacy"` are deleted during mirror cleanup, so structured rows written by achievements, gacha, mailbox, recruitment, or future feature systems survive legacy refresh.
- `server/roomBroadcasts.js` declares a tested persistence policy for realtime broadcast categories. Full room updates and default patches remain forced persistence paths; clock and presence patch categories remain lightweight/throttled. This is a guardrail for future protocol work, not a full room protocol rewrite.

# 2 核 2G 单实例容量保护与指标

当前默认软门槛为 500 在线用户、100 活跃房间和每房 20 名观战者，可通过 `MAX_ONLINE_USERS`、`MAX_ACTIVE_ROOMS`、`MAX_SPECTATORS_PER_ROOM` 下调。它们是未经目标云机压测前的保护线，不是容量承诺。达到任一门槛时停止接纳对应的新匹配、约战或观战，现有对局、玩家重连与原观战者重连继续工作。单实例 + SQLite 仍是当前唯一受支持的生产拓扑；在房间、匹配、在线状态共享化前不能用 PM2 cluster 或多副本扩容。

管理员概况的服务健康区域会暴露在线/房间/匹配/观战计数、持久化 backlog、RSS/heap、进程 CPU、event-loop delay/utilization、动作 ack 成功/失败/重复/排空拒绝、软容量拒绝、恢复原因和结果。完整 `room:update` 会记录 viewer-specific 视图构建耗时，并每 50 次抽样一次 JSON 字节数，避免可观测本身成为显著负载。

Phase 2 已删除观战 payload 内重复的黑方完整视图、把首次房间创建的 `match:found + room:update` 收敛为一份权威快照，并以 100ms debounce 合并大厅统计广播。后台可用 `lobbyStatsBroadcastEmissions / lobbyStatsBroadcastRequests` 观察合并效果。后续 move/skill delta 必须继续沿用现有 revision、gap detection 和 full snapshot 恢复合同，不能用不连续增量替代权威恢复。

上线初期应以 `ack p95 < 200ms`、`event-loop delay p95 < 50ms`、`RSS < 1.2GB`、恢复成功率大于 99%、持久化与结果保存错误为 0 作为压测观察线。只有在实际 2 核 2G 主机完成包含重连和观战的阶梯压测后，才能提高软上限。后续容量工作主要是目标机阶梯压测、静态资源 CDN 分流，以及在有完整 revision/恢复测试后按动作类型继续扩展 delta protocol。

Phase 3 已把上述观察线做成 `npm run verify:capacity`：smoke profile 使用 20 Socket/5 房和 event-loop p95 150ms 本地诊断线验证工具链，target profile 使用 500 Socket/100 房、每房 2 名观战、7.5 秒动作间隔、20% 重连、event-loop p95 50ms 目标机验收线并执行一次 SIGTERM 恢复。脚本使用独立临时数据库和 `NODE_ENV=capacity`，通过仅限 verification 环境的认证夹具把首个容量账号提升为指标读取管理员，报告冷登录/静态入口、ack/reconnect/resume 分位数，以及真实管理员运行指标快照；`artifacts/capacity/` 仅保存本机报告且不提交。该入口禁止连接正式生产数据库，本机 smoke 通过也不是容量承诺。

阶段 3 的完整本地发布候选入口为 `npm run verify:release-candidate`，按 Prisma Client、迁移基线、生产配置、构建、双项目稳定性、SQLite 备份恢复演练和容量 smoke 的顺序失败即停。稳定性环境通过 run/context namespace 隔离认证与 API 限流桶，Aemeath 等非默认角色由仅限 stability/capacity 且显式启用测试 action 的认证夹具准备；生产环境不挂钩用户名、不读取 namespace 绕过限流，也不能使用夹具路由。`npm ci` 的 postinstall 与生产 prestart 都生成 Prisma Client，确保干净安装可直接进入验证。

SQLite 运维入口 `npm run backup:sqlite -- --source <db> --output <backup>` 拒绝源/目标相同、拒绝覆盖现有输出并默认拒绝仓库 `prisma/dev.db`，随后使用 `VACUUM INTO` 和 `integrity_check` 生成一致性备份。`npm run verify:backup-restore` 只在 `.tmp/backup-restore/` 创建迁移后的源库、备份与恢复副本，借助哨兵数据验证恢复点不会被源库后续写入污染；正式恢复仍要求停服、保存故障现场、校验完整性并记录备份时间点后的数据损失。

静态流量的生产边界由 `deploy/nginx/sigrikago.conf` 与共享的 `deploy/nginx/sigrikago-routes.conf` 固化：Nginx 直接发送并 gzip `dist` 文本产物，直接发送 `/assets/` 和 `/uploads/`，Node 只处理实时 Socket、API 与健康检查。Vite hash CSS/JS 使用一年 immutable；普通稳定文件名图片/音频使用 `no-cache` 条件请求，避免同 URL 替换后继续命中旧视觉资源；SPA HTML 同样 no-cache，并保留严格的同源脚本 CSP，只在 `worker-src` 放行 Pixi 动态图片解码需要的 Blob Worker。`deploy/update-production.sh` 先以 `set -a` 导出项目 `.env`，使生产检查、Prisma 和其他子进程继承 systemd 使用的同一配置；随后在停服前以私有权限完成数据库备份，再恢复 Nginx 可读的构建权限并完成仅快进拉取、`npm ci --include=dev` 锁定依赖安装、暂存目录构建、生产配置检查和 `nginx -t`。显式包含 devDependencies 是因为 Vite 属于构建期依赖，而生产 `NODE_ENV` 默认会省略它；该顺序不会在旧站仍服务时清空现有 `dist` 或激活不可读产物。实际停机窗口限制在迁移、完整非用户后台快照同步、完整产物切换、reload、启动与 readiness 等待，失败不会强推或重置仓库。登录资源清单把商店、库存、非当前角色、战斗音轨和语音移到后台队列；战斗加载只阻塞实际选中的 battle/skill 音轨和当前房间资源，从而避免 97MB 音乐目录在冷登录或每次匹配时形成源站突发。
