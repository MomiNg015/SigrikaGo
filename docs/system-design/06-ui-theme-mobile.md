# UI 主题、移动端与交互体验

本文记录 Bright School 主题、CSS 分层、移动端适配、弹窗布局、反馈消息和 UI 交互体验。新增主题、移动布局、弹窗视觉合同或用户反馈界面时优先更新本分篇。

## 当前结论

- 玩家侧目前只有 Bright School 一个默认主题，但主题注册、作用域和 CSS 入口仍保留扩展口。
- `src/styles/base.css`、`room.css`、`modals.css`、`commerce-settings.css`、`responsive.css`、`mobile-room.css`、`hud-components.css`、`mobile-adaptive.css` 和后台/剧情教学路由 CSS 都保持 import-only 入口加领域子目录的结构；低频路由 CSS 由 lazy owner 组件导入，最终 `mobile-adaptive.css` 仍在主题之后作为手机、窄桌面和后台全屏安全层。
- Bright School 根入口当前顺序是 `base.css`、`gallery-polish.css`、`surface-contracts.css`、`component-repairs.css`、`qa-guard.css`。`surface-contracts.css` 是显式表面合同层，委托到 `surface-contracts/` 下的 root/surface/controls/forms/badges、known HUD reset、home/profile/commerce/room cleanup、final explicit surfaces、announcement controls 和 typography 分篇；它替代旧广域兜底清理结构，不再允许 broad substring selector、空兼容文件或主题级 `*` 阴影清理。
- Bright School 的高频视觉工作仍进入 owning domain：大厅和主面板在 `home/`，商业在 `commerce/`，弹窗/设置/结果/房间浮层在 `modals/`，技能/棋盘动效在 `effects/`，对局可读性在 `room/`，移动端在 `mobile/`，意图明确的纸张/手账细节恢复在 `component-repairs/`，质量和移动兜底由 `qa-guard.css` 后置导入。
- 低频路由 CSS 不再要求进入全局根样式：`src/styles/admin.css` 是后台管理 domain entry，但由 lazy `src/admin/AdminConsole.jsx` 导入；`src/styles/room/tutorial-battle-screen.css` 是剧情教学对弈专属 entry，由 lazy `src/tutorial/TutorialBattleScreen.jsx` 导入，包含桌面和移动教学战斗空角色位、目标/行动、独立 `target-ring.css` 目标光圈和 loading motion 规则。`src/styles/mobile-adaptive/admin-fullscreen.css` 仍保留在全局最终安全层中，因为它需要在主题和 HUD 之后清理 `.admin-screen` 的全屏背景继承。
- 后台管理是浅色生产工具界面，即使复用 `.primary-action`、`.secondary-action`、`.danger-action`、`.close-button`、`.modal-backdrop`、`.confirm-modal`、普通 `input`/`textarea`/`select` 或带 `setting` 片段的容器，也必须由 `src/styles/admin/polish.css` 与公告管理样式在 `.admin-screen` 内显式复位 `clip-path`、暗色/霓虹背景、绿色终端边线、text-shadow/filter 和终端 pseudo-element；该合同同时覆盖桌面端和移动端，避免 Startorch/HUD 的黑底、绿纹、斜角控件和黑色输入框污染后台。
- 移动端布局由共享移动层、Bright School 移动层和最终 `mobile-adaptive.css` 安全层共同约束。设置弹窗在最终手机层使用标题、tab、内部面板三行网格，外壳不滚动，当前 `settings-panel` 自己滚动并 containment；关闭按钮、首页图标按钮和手机菜单按钮保持显式 accessible label 与 44px 触控目标。
- 视觉合同应靠 CSS contract tests 锁定，避免后续主题覆盖把语义状态、关闭按钮、移动列表等打散。
- Board move preview and mobile touch-confirmation markers must stay centered by the `.point` absolute coordinate contract: each point receives `--board-point-center-x/y`, sits on the same intersection as SVG grid lines, and centers its preview pseudo-element internally. The shared `.board .point` rule repeats `transform: translate(-50%, -50%) !important` so later generic button hover/active transforms cannot shift board points into grid cells. ChangLi's extra-turn placements reuse ordinary move placement hints, so they must stay on the same intersections as stones and SVG grid lines. Mobile touch confirmation must render only the inner `.touch-confirm-marker`; `.point.touch-confirming::before` stays hidden, and confirmation feedback may brighten the point but must not drop the centering transform. If a mobile press state scales a point, it must compose with `translate(-50%, -50%)`, and reduced-motion states must keep the same translate so stones do not animate from grid cells back to intersections after placement.

## Modal Layering

- Shared `.modal-backdrop` stacks above room `--room-floating-z` surfaces so request and confirmation modals dim skill chips, chat controls, and room member popovers together.
- Mobile home and room floating controls use explicit local z-index tokens instead of ad hoc fixed layer numbers. Bright School portrait home sets `--home-floating-z: 120` on `.home-top-strip` and applies it to `.home-mobile-menu` plus `.home-mobile-menu-panel`, keeping the folded action menu above the home main panel. Mobile battle rooms set `--room-floating-z: 120` in base and final mobile layers; opened room menus, chat widgets, chat popovers, and `.mobile-room-dock:has(.chat-widget.open)` use that token while preserving modal-backdrop overrides that intentionally lower room controls under active modals.
- Player story playback uses a dedicated top modal layer on `.onboarding-story-backdrop`, above ordinary `.modal-backdrop` sheets and the final mobile modal safeguard, so item-triggered stories remain clickable while the warehouse or other business modal stays underneath. Story dismissal is centralized: opening the generic player clears the legacy onboarding-story flag, and closing/skipping/back dismissal clears both story overlay flags plus the active script. Admin embedded story previews reset that backdrop to normal document stacking with `z-index: auto`.
- Mobile room portraits do not render character-chain badges; duplicate-chain data remains in user payloads but is hidden on player-facing portrait surfaces.
- Battle result modals are player-centered. `src/modals/gameLifecycle/ResultModal.jsx` keeps winner color only for result semantics, but the portrait, candy item effects, chain badge, and `UserIdentity` come from the current user's room player when available. The modal emits `result-outcome-win`, `result-outcome-loss`, `result-outcome-draw`, or `result-outcome-spectator`: win shows `赢了耶！` with the existing portrait hop, loss shows `输掉了...` with a grayscale frozen portrait plus `/assets/effects/result-defeat-rain.gif`, and draw/observer states keep the panel compact without victory motion.
- Desktop, Startorch terminal, Bright School, and final mobile result styles must keep the outcome label first and keep loss rain sized from `--result-defeat-weather-width/top`. Result reward tiles are intentionally filled rather than transparent: `result-reward-negative` uses a pale red surface, `result-reward-nonnegative` uses pale green, and `result-reward-coins` uses pale gold, with terminal/Bright School/mobile overrides preserving those semantic fills. The inner `.text-rating-value` in result rewards keeps only the semantic numeric font and must not draw its own background, border, or shadow. Mobile result sheets collapse to one column, cap the portrait through `--result-portrait-size`, and center the confirm action without reintroducing a winner-only layout.

## Feedback Messages

- Player feedback is persisted in the `FeedbackMessage` Prisma model, backed by the `202605250001_add_feedback_message` migration.
- Logged-in users submit feedback through `POST /api/feedback`; the server stores `userId`, current `username`, normalized `content`, and `createdAt`.
- Feedback content strips control characters, trims whitespace, rejects empty submissions, and caps content at 400 characters.
- The home and room message-board modal calls the feedback API. On success it closes the modal and shows a green top toast: `感谢您的反馈！`.
- The message-board textarea uses the same 400-character limit, displays the remaining character count below the input, and defaults to a taller writing area on desktop while mobile clamps the height to the viewport.
- Admins can view the latest 100 feedback messages through `GET /api/admin/feedback`.
- The admin console includes a `留言反馈` tab that displays submit time, username, and full feedback content with wrapping for longer text.
