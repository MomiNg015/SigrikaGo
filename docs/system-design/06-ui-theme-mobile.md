# UI 主题、移动端与交互体验

本文记录 Bright School 主题、CSS 分层、移动端适配、弹窗布局、反馈消息和 UI 交互体验。新增主题、移动布局、弹窗视觉合同或用户反馈界面时优先更新本分篇。

## 当前结论

- 玩家侧目前只有 Bright School 一个默认主题，但主题注册、作用域和 CSS 入口仍保留扩展口。
- `src/styles/base.css`、`room.css`、`modals.css`、`commerce-settings.css`、`responsive.css`、`mobile-room.css`、`hud-components.css`、`mobile-adaptive.css` 和后台/剧情教学路由 CSS 都保持 import-only 入口加领域子目录的结构；低频路由 CSS 由 lazy owner 组件导入，最终 `mobile-adaptive.css` 仍在主题之后作为手机、窄桌面和后台全屏安全层。
- Bright School 根入口当前顺序是 `base.css`、`gallery-polish.css`、`surface-contracts.css`、`component-repairs.css`、`qa-guard.css`。`surface-contracts.css` 是显式表面合同层，委托到 `surface-contracts/` 下的 root/surface/controls/forms/badges、known HUD reset、home/profile/commerce/room cleanup、final explicit surfaces、announcement controls 和 typography 分篇；它替代旧广域兜底清理结构，不再允许 broad substring selector、空兼容文件或主题级 `*` 阴影清理。
- Bright School 的高频视觉工作仍进入 owning domain：大厅和主面板在 `home/`，商业在 `commerce/`，弹窗/设置/结果/房间浮层在 `modals/`，技能/棋盘动效在 `effects/`，对局可读性在 `room/`，移动端在 `mobile/`，意图明确的纸张/手账细节恢复在 `component-repairs/`，质量和移动兜底由 `qa-guard.css` 后置导入。
- Bright School 的 `.app-shell.player-theme-enabled.theme-bright-school .modal-backdrop` 由 `surface-contracts/root-shell.css` 显式覆盖为暗色静态遮罩，并同时声明 WebKit 前缀和标准 `backdrop-filter: none !important`；标准声明保持在前缀之后，避免生产 Lightning CSS 压缩只保留前缀而让 Chrome 回退到基础层 `blur(9px)`。`npm run check:built-css` 在 Vite build 后直接检查 `dist` 中的最终压缩 CSS，且已进入 `npm run check` 和正式更新脚本。
- 低频路由 CSS 不再要求进入全局根样式：`src/styles/admin.css` 是后台管理 domain entry，但由 lazy `src/admin/AdminConsole.jsx` 导入；`src/styles/room/tutorial-battle-screen.css` 是剧情教学对弈专属 entry，由 lazy `src/tutorial/TutorialBattleScreen.jsx` 导入，包含桌面和移动教学战斗空角色位、目标/行动、独立 `target-ring.css` 目标光圈和 loading motion 规则。`src/styles/mobile-adaptive/admin-fullscreen.css` 仍保留在全局最终安全层中，因为它需要在主题和 HUD 之后清理 `.admin-screen` 的全屏背景继承。
- 后台管理是浅色生产工具界面，即使复用 `.primary-action`、`.secondary-action`、`.danger-action`、`.close-button`、`.modal-backdrop`、`.confirm-modal`、普通 `input`/`textarea`/`select` 或带 `setting` 片段的容器，也必须由 `src/styles/admin/polish.css` 与公告管理样式在 `.admin-screen` 内显式复位 `clip-path`、暗色/霓虹背景、绿色终端边线、text-shadow/filter 和终端 pseudo-element；该合同同时覆盖桌面端和移动端，避免 Startorch/HUD 的黑底、绿纹、斜角控件和黑色输入框污染后台。
- 移动端布局由共享移动层、Bright School 移动层和最终 `mobile-adaptive.css` 安全层共同约束。设置弹窗在最终手机层使用标题、tab、内部面板三行网格，外壳不滚动，当前 `settings-panel` 自己滚动并 containment；关闭按钮、首页图标按钮和手机菜单按钮保持显式 accessible label 与 44px 触控目标。
- 视觉合同应靠 CSS contract tests 锁定，避免后续主题覆盖把语义状态、关闭按钮、移动列表等打散。
- 衣柜服装详情保留共享 `.shop-detail-art` 图像框，但由 `.character-costume-detail-art` 在基础层和 Bright School 最终主题层共同清除立绘的 `drop-shadow`；该覆盖不作用于商店商品详情立绘，也不移除图像框或弹窗阴影。
- Bright School 下扎希拉与娜波摩的台词气泡使用两张 ImageGen 完整透明 WebP 框图：扎希拉是淡莓白手切纸片并从右下指向立绘，娜波摩是暖金票券纸片并从左下指向立绘。纸纹、手绘轮廓、硬影和尾巴全部位于图片画布内部，CSS 清除旧边框、阴影、圆角与三角伪元素，只以 `100% 100%` 背景承载框图并把实时 DOM 台词放在安全内边距中，因此多层商店 `overflow: hidden` 不会单独裁掉尾巴或阴影。竖屏最终层只调整框图宽度、位置、字号与内边距，两套气泡的文字左右安全区统一为 `22px`，保持文本、切换木牌和看板娘互不遮挡；其中残星会气泡重复 Bright School 完整主题作用域，以右侧 `54%` 的竖屏布局胜过桌面的 `80%` 重要规则，避免遮住娜波摩面部。
- 商店双页的切换路牌在桌面和竖屏都使用镜像底角锚点：扎希拉页位于左下，残星会页位于右下；桌面统一使用 `14px` 边距，最终移动层统一使用 `8px` 边距，并显式清除顶部与相反方向的 inset。
- 商店页头余额与履历金币共用 `.shop-wallet` 的黄金币渐变、深色描边、硬阴影和 `CircleDollarSign` 图标；商店 owner 只压缩竖屏尺寸，不再声明会覆盖共享渐变的纯色背景。
- IRIS Database 是首页自有的视口固定入口而不是舞台网格项。`src/home/IrisDatabase.jsx` 持有本地打开状态并复用共享 `ModalDialog`；入口和弹窗完整使用数据流原型 v2 的深蓝/绿色、切角、断线节点、点阵数据字与扫描语法，入口与窗口的立绘槽都不渲染 `<img>` 或请求候选人物资源。`src/styles/base/foundation.css` 将内置 `public/assets/fonts/DottedSongtiCircleRegular.otf` 注册为 IRIS 专用 `Dotted Songti Circle` 字体：入口整体只用该字体；窗口使用 WuWa 拉丁/数字字形在前、`Dotted Songti Circle` 字体在后的组合栈，因此英文和数字走 WuWa，中文与符号走`Dotted Songti Circle` 字体；友情链接索引列表在自身 owner 中覆盖为全 `Dotted Songti Circle` 字体，Bright School 的最终字体胜出规则独立放在 `themes/bright-school/modals/iris-database-typography.css`。桌面窗口采用左侧空立绘数据扇区/右侧编号链接记录，竖屏移动端采用上方立绘扇区/下方记录列表；不再由 Bright School 把右栏覆盖成米白纸面，也不使用圆角外壳、圆角资料行或围棋棋子列表。问候语绝对定位在立绘扇区顶部 8%（竖屏 13%），立绘扫描框从 20%（竖屏 34%）开始，二者测量不重叠；通讯条始终完整显示 `irisGreeting` 台词池中本次打开时随机选中的一条，不再自动收起、响应点击或显示收起态。资料列表自身使用 `overflow-y: auto`、`overscroll-behavior: contain` 和稳定滚动条槽，条目增加时不撑高窗口。问候语池由共享规范化器限制为最多 12 条、每条 80 字，并兼容旧数据库中的单条纯文本；链接限制为最多 30 条安全 HTTP(S) 地址，并在后台“看板娘管理”页的 IRIS 分区一起编辑。编辑页加载完成前不显示可编辑草稿，加载完成后仅 token 改变会重新取数，父层重渲染与字段换焦不会覆盖未保存输入。入口使用 safe-area 右偏移、保持现有宽度并以 1.56 宽高比把原高度减半，同时维持 44px 以上触控面，低于弹窗遮罩与手机菜单层；样式按 entry、shell、greeting、portrait、archive、records 与 Bright School winner 分开持有，扫描和边缘流动具备 reduced-motion 停止态。
- 商店窗口在同一 `ModalDialog` 内挂载扎希拉商铺与残星会服装店，两页用 240ms transform 平移切换并在 reduced-motion 下取消过渡；每页保留独立目录、批次、1 秒刷新冷却和错误重试状态。窗口自身是固定裁切容器而非滚动 owner，因此 `window-redesign.css` 显式使用 `overflow: hidden` 与 `scrollbar-gutter: auto`，抵消通用 modal 的双侧稳定滚动条槽，使 header、200% 双页滑轨及两家商店背景在桌面和竖屏都直接贴合边框内缘。Bright School 竖屏首页的通用 `max-width` 保护只作用于 `.home-screen` 后代，不能压缩商店的 200% 双页滑轨。扎希拉 `data-store="zahira"` 页头使用简单的蓝灰—灰紫低细节配色条，不裁切或模拟主体桌面场景；页头只渲染一份当前激活目录的实时金币余额，顺序固定为刷新、标题、金币、关闭，不再在两家接待区复制钱包。手机最终层使用 `44px minmax(0, 1fr) max-content 44px` 四列网格，把通用模态框关闭按钮恢复为静态网格项，使关闭和刷新两个 44px 控件垂直居中，并让金币紧邻关闭按钮左侧。服装店使用版本化深红粗蜡笔舞台图，页头标题固定为不换行且完整显示的“残星会cosplay部”；`data-store="costume"` 的页头复用桌面舞台图顶部帷幕，并以深红、黑梅低对比色块延续粗蜡笔舞台，暖象牙标题与现有浅色纸面按钮在桌面和竖屏共用同一语义 owner。两页切换按钮共同使用 `.shop-switch-button`，文案只保留实时 DOM“残星会”与“扎希拉商店”；路标改用 ImageGen 生成的 `1420x430` 透明无损贴纸 WebP，扁平箭头板、极短支撑脚、暖白模切边、酒红粗轮廓、少量蜡笔纹和两颗简化钉点全部在图内，不再绘制写实木纹、绳结、裂口或立体倒角，右向原图只在 `::before` 图片层通过 `scaleX()` 镜像成左向，按钮文字不会反转。对应透明 PNG 作为源图保留，WebP 通过 `SHOP_DIRECTION_SIGN_IMAGE` 进入商店关键图片预加载；旧 CSS 渐变板面、clip-path 外形和铆钉伪元素不再渲染。桌面与竖屏触控面都至少 48px 高；hover/focus 保留轻微上移、旋转和提亮，但不再应用 drop-shadow，避免移动阴影与背景产生错位，active 仅轻压，reduced-motion 下不位移。桌面图按左侧约 34% 娜波摩接待、右侧约 65% 最多五件服装的低细节舞台构图，竖屏独立图按上方约 57% 商品舞台、下方约 43% 看板娘/气泡接待区构图。两张图都使用与扎希拉背景一致的蜡笔颗粒、纸张纹理、歪斜轮廓和简化色块，并以居中 `cover` 覆盖 `.costume-store-panel`；最终移动层通过 `--costume-shop-mobile-background-image` 直接选择竖图，不运行时裁切横图，也不叠加旧幕布伪元素。两端的服装商品舞台都复用扎希拉商店的实际容器测量与 `layoutShopCards` 数量感知排布，按当前 1–5 件商品动态选择单排或平衡双排、逐行居中且不保留空槽；每批服装复用 6–9px 浮动值与 4.2–6 秒周期，桌面按 2 倍呈现 12–18px 总行程，竖屏按 1.5 倍呈现 9–13.5px 总行程，悬停/聚焦/按下时暂停，减少动态效果时停止连续动画。五张商品图使用裁到 alpha 内容边界的矩形 WebP，`.costume-shop-art` 随实际立绘尺寸收缩，售价绝对定位到该锚点右下角并与可见立绘少量重叠；该视觉层在不改变共享槽位、点击框或排布算法的前提下，桌面缩放为 1.14、竖屏缩放为 1.18，立绘与售价共同位于旋转/浮动包装内并始终同步变换。桌面悬停保留原位移动效但卡片背景保持透明，只在立绘后方显示局部暖金舞台光。旧钱包 WebP 保留为历史资产但不再运行引用或预加载；未拥有对应角色的服装卡只灰化立绘，仍可打开详情，购买按钮不可用。
- 部员手册角色详情的衣服图标始终可点，桌面位于立绘区右上角、移动端移到左上角以避开关闭按钮。服装选择通过 portal 挂到主题应用根并使用独立顶层遮罩，不受部员手册父窗口的布局与裁剪影响；窗口只显示“{角色名}的衣柜”标题，不显示副标题、“只有默认服装”等解释性文案；列表固定“默认服装”第一、当前非默认服装第二、其他已拥有服装随后、未拥有服装最后。卡片主体打开详情且必须保持透明、无边框和无额外阴影，让外层卡片承担与部员手册角色卡片一致的纸卡轮廓；独立衣服按钮即时装扮。当前服装仅以外层浅绿色卡片背景表达，并通过 `aria-current` 保留语义，不显示“装扮中”文案。服装详情在桌面与移动端都直接复用扎希拉商品详情模板：立绘位于 `.shop-detail-art` 图像框，右侧/下方文案区依次显示“{角色名}服装”分类胶囊、服装名、左对齐 illust 和独立说明框；不渲染持有状态区域，竖屏继续沿用商品详情的一列响应式布局。非默认服装的衣柜缩略图与全局实际装扮立绘读取同一套逐服装缩放/偏移校准；校准使用独立 CSS transform 属性与既有交互动效合成，不改变卡片布局盒，也不作用于商店商品图和详情大图。未拥有服装与未拥有角色的装扮按钮使用原生 disabled，不增加额外提示；默认服装不灰化。移动端规则由 `modals/character-opening/costume-wardrobe-mobile.css` 单独拥有服装列表，服装网格为两列、内部滚动，卡内立绘与装扮按钮纵向排列并水平居中；服装详情使用应用根下的第二个固定定位顶层遮罩，与衣柜窗口互为同级，不能作为衣柜内部的相对定位子层。
- Board move preview and mobile touch-confirmation markers must stay centered by the `.point` absolute coordinate contract: each point receives `--board-point-center-x/y`, sits on the same intersection as SVG grid lines, and centers its preview pseudo-element internally. The shared `.board .point` rule repeats `transform: translate(-50%, -50%) !important` so later generic button hover/active transforms cannot shift board points into grid cells. ChangLi's extra-turn placements reuse ordinary move placement hints, so they must stay on the same intersections as stones and SVG grid lines. Mobile touch confirmation must render only the inner `.touch-confirm-marker`; `.point.touch-confirming::before` stays hidden, and confirmation feedback may brighten the point but must not drop the centering transform. If a mobile press state scales a point, it must compose with `translate(-50%, -50%)`, and reduced-motion states must keep the same translate so stones do not animate from grid cells back to intersections after placement.
- Tailwind CSS is available only as a low-intrusion utility layer through `src/styles/tailwind.css`, imported from `src/styles.css` after `hud-components.css` and immediately before `src/styles/themes.css`. It uses the Tailwind v4 Vite plugin, imports `tailwindcss/theme.css`, `src/styles/tailwind/tokens.css`, and `tailwindcss/utilities.css` with `prefix(tw)` on Tailwind imports and `source("../")` on the utilities import, and deliberately omits preflight so Bright School, board, modal, and mobile safety layers keep their existing element and component contracts. Tailwind is a staged long-term target with its full execution plan persisted at `.trellis/tasks/07-01-tailwind-migration-roadmap/tailwind-full-migration-plan.md`: phase 1 records contracts and the `@theme inline` semantic token scaffold without migrating JSX, phase 2 pilots `tw:` utilities in new or isolated admin/tooling surfaces, phase 3 creates UI primitives, phase 4 migrates shared modal/list/card/form internals, phase 5 migrates home/lobby/commerce non-gameplay flows, phase 6 tokenises Bright School, and phase 7 reduces final mobile safety layers only after component ownership and visual checks exist. The current Phase 2 pilot is limited to admin table shells: `AdminAudit` first proved the `tw:max-w-full`/`tw:overflow-x-auto` utility path, and Phase 3 now routes all admin `.admin-table-wrap` shells through `AdminTableScroll` backed by `src/ui/primitives/ScrollArea.jsx` while existing CSS keeps visual shell rules. Phase 3 also includes `src/ui/primitives/Badge.jsx` for low-risk inline status badge layout utilities, `src/ui/primitives/EmptyState.jsx` for admin table empty-cell alignment/spacing through `AdminTableEmpty`, and `src/ui/primitives/Button.jsx` for admin action alignment through `AdminActionButton`, with visual styling still owned by existing CSS. Phase 4 has started only with `src/modals/modalComponents.jsx` `ModalActionButton`, used by `ConfirmModal`, `MessageBoardModal`, simple `AnnouncementModal` retry/load-more actions, the `PersonalizationModal` save action, the `MailboxModal` attachment claim action, the `FriendsOverlays` duel-mode cancel action, and the `UserProfileCard` profile report submit action to route modal action alignment through `Button` while preserving existing `.danger-action`, `.secondary-action`, and `.primary-action` visual contracts. Current room gameplay, board geometry, skill presentation, Pixi canvas hosts, player-facing button restyling, mailbox list rows/delete controls, friends match-mode option buttons, profile confirm panels, profile social action buttons, Bright School final mobile gameplay safety, and mobile gameplay controls stay CSS-entry owned.
- Current Phase 5 has started only with `src/home/homeComponents.jsx` `HomeActionButton`, used by the home match-mode picker cancel action to route alignment through `Button` while preserving the existing `.secondary-action` visual contract. The match-mode option buttons, modal spacing contracts, home artboard, utility entries, player plaque art, decorative imagery, and final mobile safety rules remain CSS-owned until a full home/lobby/commerce surface has focused desktop/mobile tests and visual checks.
- Current Phase 6 has started only as a no-visual-change token contract: `src/styles/tailwind/tokens.css` maps Bright School paper, clean surface, ink, border, accent, and paper-shadow variables into Tailwind semantic tokens, while Bright School value ownership remains in `surface-contracts/final-root-surfaces.css` and `quality-base/refinement-foundation.css`. Current Phase 7 has started only as `cssLayerInventory` registration for the `mobile-adaptive.css` final guard reduction candidate; the final mobile layer remains after `themes.css` until replacement component ownership is proven on phone portrait, small landscape, narrow desktop, and regular desktop.
- Accent typography is semantic and opt-in. `src/styles/base/foundation.css` owns `"Sigrika Accent Latin"` plus `--font-display-accent`, `--font-numeric-accent`, `.text-display-accent`, `.text-clock-value`, and `.text-rating-value`; the font is not a global UI replacement. Chess clock digits use `.text-clock-value`, player-visible rating values use `.text-rating-value`, and only player-side atmosphere labels such as the login `SigrikaGo` subtitle use `.text-display-accent`. Home student-ID plaque rank digits are a narrow owner-CSS exception: `.plaque-mode-rank` uses `--font-numeric-accent` directly for the displayed number only, without applying `.text-rating-value` to non-rating data. These accent classes use `text-transform: uppercase` so lowercase Latin source text visually renders as uppercase art lettering without mutating the underlying string. Usernames/UserIdentity, admin, body copy, chat/announcements, form inputs, coins, prices, stock, probabilities, game-count/record numbers, room codes, move counts, dates, timestamps, and leaderboard rank positions keep the normal UI font. Because Bright School has late broad readability guards with `!important`, `src/styles/mobile-adaptive/semantic-accent-typography.css` is the final post-theme guard that reapplies the semantic font tokens and uppercase transform, restores clock state colors and timer track variables, clears accidental background/border/shadow from `.text-clock-value`, keeps main-time clock digits at dark `#1c171a` instead of gray while preserving byo-yomi warning colors, deliberately avoids changing `.digital-timer` card background or border styling, and applies a mobile-only compact clock sizing override so player-strip timer tracks stay inside their container after the art font loads.
- Window-title typography is a separate semantic contract. `src/styles/base/foundation.css` registers `public/assets/fonts/LXGWMarkerGothic-Regular.ttf` as `"Sigrika Window Title"` and exposes `--font-window-title`; `.text-window-title` applies it to the home main title, while dialog/backdrop-scoped `h2` selectors cover player-facing window titles without changing body copy, controls, subtitles, or numeric text.
